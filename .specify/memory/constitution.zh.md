# Coffer 章程

> English: [constitution.md](./constitution.md)

> Coffer 是一个本地优先的 AI agent 仓库 (vault)：开发者沉淀下来的 AI 资产
> 全部留在本机，任何 AI agent（Claude Code、Codex、未来的新成员）都通过
> 同一个安全接口进行读取与贡献。
>
> 本章程仅约定**脚手架层级**的不变量：技术栈、工作流、许可证立场与架构
> 风格。产品行为本身——资源模型、安全/审批规则、对外暴露的接口面 (surface)
> 清单、各类数据的落盘位置——由 `specs/` 下的逐 feature 规范定义。

## 核心原则 (Core Principles)

### 原则 1：本地优先 (Local-First, 不可妥协)

所有用户数据都驻留在用户的机器上。云服务仅作为 LLM 与工具的提供方——
它们绝不充当任何仓库状态的事实记录方 (system of record)。HTTP API 仅绑定
到 `127.0.0.1`。若要把用户态复制到任何由厂商掌控的云端，必须走章程修订
流程。

Coffer 可以把仓库**导出**到用户选定的目录，也可以把导出**导入**回来，
使用户能在自己的多台机器之间搬迁仓库。这属于用户掌控下的普通本地文件
输出：它不产生第二个事实记录方，也不会把任何数据复制到厂商掌控的服务。

**例外——用户自有的备份远端。** Coffer 可以把导出推送到用户自己持有的
git 远端，使硬盘损坏或误删除得以恢复。该例外受四项条件约束，缺一不可：
远端**仅作备份**、永不充当事实记录方——本机仓库始终权威，恢复必须是用户
的显式动作；复制是**单向**的——Coffer 只推送、不合并，因此不授权任何收敛
机制；密钥**只以密文形式**流转，主密钥除带外传递外绝不离开本机；该功能
**默认关闭**，由用户针对自己持有的仓库主动开启。由 Coffer 自行运营的托管
端点仍在此例外之外。

### 原则 2：规范即真理 (Spec-as-Truth, Spec-Driven Development)

`specs/` 目录下的规范是产品契约的唯一权威。任何会改变对外可见行为的 PR
都必须**先**更新对应规范，再改代码。规范不是「文档」——它就是实现的
契约；当代码与规范不一致时，错的是代码。

### 原则 3：从第一天起就为开源做好准备 (Open-Source-Readiness from Day One)

许可证 (MIT)、治理规则、贡献流程、Conventional Commits 必须从 v0.0.1
起就存在于仓库中，而不是事后补齐。任何会让这份清单变短的改动——引入
未经豁免的闭源依赖、省略 AI 生成内容的署名——都视为违反本原则，必须
通过章程修订并附带明确的迁移方案。

## 技术与架构约束 (Technology & Architectural Constraints)

- **语言。** 后端、CLI 及任何 MCP 适配层使用 Python 3.12+；前端使用
  TypeScript 5.x。在未走章程修订的情况下，不引入其他主语言。
- **架构。** 分层：`surfaces → application → domain → infrastructure`。
  `domain/` 不得 import `infrastructure/`、`surfaces/` 或任何外部 SDK；
  `application/` 不得 import `surfaces/`。跨层公共模块只在第二个 feature
  也需要它时才抽取。（例外：Resource 框架——见
  [Resource Framework Upfront](../../docs/decisions/resource-framework-upfront.md)。）
- **持久化。** SQLite 是控制面状态的事实记录方。批量用户内容（按规范
  引入时）以文件形式存放于本地文件系统，按需建立索引。
- **凭据。** 密钥**只**以 Fernet 密文形式存放于 `credentials` 表；明文仅在
  解密与拉起子进程/注入 header（消费密钥处）之间短暂存在于内存。Fernet 主
  密钥由 `coffer.infrastructure.credentials` 独占管理——默认为 DB 旁的
  `0600` 文件，opt-in 时通过 `keyring` 存于操作系统钥匙串。`keyring` 的
  import 仅限该模块。其他代码一律只持有凭据引用 (credential ref)。任何密钥
  明文都不得进入数据库、日志、审计或任何结构化事件。凭据材料只以 Fernet
  密文形式离开本机，且仅在用户明确要求时；主密钥绝不写入导出物，需带外
  引导到另一台机器。
- **网络默认值。** 仅监听 loopback。一旦需要发起对外 HTTP，必须经过一
  个具备 SSRF 防护的客户端。一旦需要对公网暴露任何 surface，必须以独立
  进程运行，并仅限于经过签名校验的回调路径。

## 质量门槛 (Quality Gates)

只有在**全部**满足以下条件后，一项变更才算「完成」：

- 相关的 `spec.md` 已更新到与代码一致。
- `spec.md` 中的验收场景覆盖了新增行为并能通过。
- `make verify` 在本地与 CI 均通过。
- 文件大小限制 (见 `agents/stack.md`) 仍然成立。
- 架构边界未被破坏。

## 治理 (Governance)

本章程**优先于** `AGENTS.md`、`CONTRIBUTING.md` 或任何单个规范文档中
任何相冲突的指引。出现分歧时，以章程为准。

**修订流程 (Amendments)。** 对任何 Core Principle、Technology &
Architectural Constraints 或 Quality Gate 的修改，必须满足：

1. 一个提案 PR，说明动机、当前行为、拟定行为、下游影响、备选方案。
2. PR 描述中明确记录决议。
3. 该 PR 同步更新本文件，并提升下方的 **Version** 字段。

**PR 评审。** 每个 PR 描述都应在适用时点出它所触及的章程原则或约束，
并解释该变更为何尊重 (或正式修订) 它们。

**Version**: 0.5.0

> **0.5.0 修订（spec vault-export-import——备份远端）。** 在原则 1 中新增*用户
> 自有备份远端*例外。动机：导出与导入回答的是「把仓库搬到另一台机器」，
> 却回答不了「硬盘坏了」和「上周误删了那个 skill」——两者都需要一份存放在
> 本机故障波及不到的地方的副本，以及一段足以回溯到失误发生之前的历史。
> 当前行为：导出只是本地文件输出，搬到哪里是用户自己的事。拟议行为：
> Coffer 可以把导出提交进 git 仓库并按定时推送到用户自有的远端，恢复则是
> 一条显式命令。下游影响：spec vault-export-import 新增备份远端、定时推送
> worker 与恢复路径；`sync_remotes` 配置与一个 git 适配器加入 sync 切片。
> **本次并非恢复 0.3.0 例外**：那一条授权的是机器之间的持续收敛，以及
> 0.4.0 随之移除的那套机器——机器身份、带 TTL 的墓碑、冲突仲裁、隔离重试
> ——它们仍然处于已移除且未授权的状态。备份是单向的，因此一样都不需要。
> 已考虑的备选方案：只提交到本地 git 仓库、推送交给用户自己做——否决，
> 因为仅存于本地的副本无法在本功能存在意义所指的那次硬盘故障中幸存。
> 由项目所有者记录决策。

> **0.4.0 修订（spec vault-export-import 范围收缩）。** 从原则 1 中移除*用户自掌控
> 同步介质*例外，并撤销 0.3.1 对其开篇句的改写。动机：基于 git 远程的
> 持续多机同步，为其保证背负了整套机制——机器身份、带 TTL 的墓碑、冲突
> 仲裁、隔离重试、git 工作区与后台 worker——而这份成本并未被仓库实际
> 在机器间搬迁的方式所回报。当前行为：仓库状态在 0.3.0 例外的三项条件下
> 持续同步到用户自有的 git 仓库。拟定行为：Coffer 把仓库导出到用户选定的
> 目录，并能把导出导入回来；没有传输介质、没有远程、没有后台复制，因此
> 也就不需要维持对原则 1 的例外。下游影响：spec vault-export-import 收窄为导出与导入；
> 机器注册表、舰队视图以及框架的机器 scope 轴随之移除；例外原本承载的
> 「只以密文离开本机」规则移入「凭据」约束，从而适用于每一次导出而不再
> 只适用于同步。已考虑的备选方案：把持续同步保留在特性开关之后——被否决，
> 因为无人使用的代码路径同样需要维护和测试。决议由项目所有者记录。

> **0.3.0 修订（spec vault-export-import）。** 为原则 1 增加*用户自掌控同步介质*例外，
> 在三项条件（不产生新的 system of record、凭证只以密文离机、用户主动开启
> 且自有）下授权基于用户自有 git 仓库的多机同步。动机：让单一用户在自己的
> 多台机器间保持同一个仓库一致，且不放弃 local-first 保证。当前行为：多机
> 同步原为明确非目标。拟定行为：在上述受限例外下允许。下游影响：新增 spec
> vault-export-import（同步引擎、CLI/HTTP 接口、daemon 自动同步 worker）；不改动凭证
> 静态存储与 loopback 绑定规则。备选方案：点对点（Syncthing 式）与用户自有
> 对象存储——为获得内建历史、diff 与合并能力，选择 git。决议由项目所有者记录。

> **0.3.1 修订（编辑性修订）。** 将原则 1 的开篇句改写为匹配 0.3.0 例外
> 已经授权的多机现实。动机：[Per-Agent Resource Scope](../../docs/decisions/per-agent-resource-scope.zh.md)
> （机器 × agent 资源作用域）把多机同步
> 进一步延伸进框架内部，印证了「本地」已经从单台机器成熟为用户的机群——
> 一个仓库，每台机器都持有完整状态——而原则的开篇句尚未跟上这一点。当前
> 表述：「所有用户数据都驻留在用户本机。」拟定表述：「所有用户数据都驻留
> 在用户的多台机器上——一个仓库，每台机器都持有完整状态。」下游影响：无
> ——纯编辑性修订；原则 1 的规则与 0.3.0 例外的三项条件均不变。决议由项目
> 所有者记录。
