## 背景

Web 端 Chat 页面被重定位过两次，核心概念也被拿掉过一次，理由每次都一样——*Coffer 是金库，
不是行动者；一个要与编码 agent 自带 UI、以及与 IM 抢位置的浏览器聊天，不会有持久的使用*。
它先被改造成 **Vault Console**（对金库说话，外加旁观并审批 channel 驱动的 turn）；随后
内置聊天人格退役，chat 只与受管 agent 对话，页面名字改回*聊天*；再随后工具审批被整体删除，
channel 那部分职责从「旁观 + 审批」缩成「旁观」。

留下来的，是一个没人决定过要留还是要杀的、被截去一半的接口面。

在梳理 channel 桥接时浮现出的那条决定性约束是：Coffer 的 channel 是**属主配对**的——
是已配对的*属主*从 IM 应用里聊天。所以所谓的「IM 对端」其实是*同一个人*，是手机上的属主，
不是第三方。于是「从浏览器接管一段 IM 会话」是**同一个属主的跨接口面连续性**，而不是
多人协作。这一下就把整个多人维度移走了：不需要对端身份模型，不需要「谁能打断谁」，
也不需要消息可见性规则。

这份记录挑出这个页面唯一不可替代的职责，并把它定下来。

## 决策

**Chat 是那些属主同时也在用手机驱动的会话的 Web 接口面。** 一个属主，一条会话时间线，
两块屏幕。一段会话背后是一个真实的 agent session（一次 resume、一个工作目录），所以
手机上发起的 turn 与浏览器里续上的 turn 命中的是**同一个** session。

在页面上，属主可以实时**旁观**任何一段会话——包括手机上发起的 turn，逐 token 地看——
**中断**正在跑的 turn，并通过自由输入**插入 / 继续**：消息入队，永不阻塞。

### 1. 一条实时会话总线

旁观 / 中断 / 插入三件事里，真正缺的只有**旁观**。中断本来就跨接口面可用（进行中的 turn
由同一个守护进程持有）；插入是前端的缺口。旁观才是真缺口：浏览器只能实时接住它自己发起的
turn，而从 IM 发起的 turn 只能靠轮询已持久化的行看到。

于是把**发起 turn** 与**消费它的事件**解耦。每段会话获得一个广播器，把当前 turn 的每个事件
追加进缓冲，并扇出给每个已接入的订阅者。四条路由承载它：

- `POST /api/v1/chat/conversations/{id}/messages`——**发起或入队**一个 turn，并立刻返回
  `202`。它不再拥有事件流。
- `GET /api/v1/chat/conversations/{id}/events`——SSE **订阅**：接入时从当前 turn 的开头
  重放，然后转为实时；没有 turn 在跑时保持打开，并在下一个 turn 开始时把它送出来，不论
  由哪个接口面发起。
- `PUT /api/v1/chat/conversations/{id}/pending`——**整体替换**待处理队列。
- `POST /api/v1/chat/conversations/{id}/interrupt`——**停止**运行中的 turn 并**挂起**队列。

**只有一条事件路径。** 所有消费都走订阅；POST 是发完即返回。于是「旁观我发起的 turn」
与「旁观手机发起的 turn」走同一段代码——发送方不是特例——而重放缓冲保证发送方不会漏掉
早期事件。

### 2. 随便发；一条 FIFO 待处理队列

「拒绝第二条消息并锁住输入框」被替换掉了：草稿区**永不锁定**，发多了的消息**入队**。
每段会话持有一条内存里的待处理队列；当前 turn 完成时，编排器出队队首、把它提交为下一条
用户消息并跑它的 turn。「每段会话同时只有一个 turn」这条不变式**保留**——处理仍是串行的，
变的只是对「发多了」的回答。

- **串行，不合并。** 每条排队消息都是它自己的一个 turn，FIFO。
- **待处理 = 未提交。** 排队消息不写进已提交的消息序列；它们以可移除的行呈现，只有在
  它们的 turn 开始时才拿到序号。编辑其中一条会把它拉回草稿区；重发则把它放到**尾部**，
  因为那是一次新的发送。
- **中断 = 停止当前 turn + 挂起队列。** 否则下一条排队消息会径直冲进刚被停掉的那个 turn。
- **跨接口面推进。** 会话上*任何*一个 turn 结束后队列都会自动推进——包括 IM 驱动的那个
  ——所以一条排在手机发起的 turn 后面的浏览器消息，在那个 turn 完成时照样会跑。而 turn
  进行中*从* IM 到来的消息，由 channel 自己的入站缓冲持有，因此保证是「网页端的发送
  永不被拒绝且按序运行」，不是「IM 与网页共用一个队列对象」。
- **队列状态走总线。** 一个队列变更事件广播有序的待处理项，于是第二个标签页和手机渲染
  出同一份行。
- **在内存里。** 守护进程重启时队列丢失，与「进行中的 turn 在重启时被标记为失败」一致。

### 3. 收起 origin，留下回信地址

在单属主前提下对端永远是属主，于是「网页 vs channel」这个二分**作为概念坍缩**了：一份
会话列表、一个草稿区、一条订阅，不按 origin 分支。但 channel 名与对端 chat id 是把 agent
输出推回 IM 应用的**回信地址**，因此它们作为可选的 channel 绑定保留——一段会话「有绑定」
当且仅当 channel 名非空——页面在有绑定时显示一个小小的「也在 Telegram/SeaTalk 上」徽标。

### 不变式

- **同一套接缝，没有旁路。** 页面只经由既有的会话端口与 turn 端口驱动 turn；agent 无从
  分辨网页 turn 与手机 turn。订阅是只读旁观加上既有的中断，它不引入任何特权 turn 路径。
- **没有多人模型。** 单属主前提是承重的；对端身份与消息可见性规则不在范围内。
- **只有受管 agent。** [Built-in Agent Is Internal](builtin-agent-is-internal-capability.zh.md)
  依然成立——没有内置聊天人格；本地模型仍只在 `coffer__*` 背后内部可用。

## 影响

- 页面及其路由描述在 spec [`channels`](../../specs/channels/spec.zh.md) 的 G 节
  （FR-072…FR-078），架在 turn 平台（FR-043…FR-055）之上；契约在该 spec 的 OpenAPI 文件里。
- 会话 schema 不带 `origin`，也不带对端显示名；channel 名与对端 chat id 作为 channel
  绑定保留。
- 前端对每段打开的会话持有一条常驻订阅，而不是「每个 turn 一条流 + 轮询」；草稿区永不
  锁定，并渲染待处理行。
- Vault Console 那套定位不随之恢复：没有金库人格，也没有审批席位
  （[Remove Tool Approval](remove-tool-approval.zh.md)）。

## 备选方案

**只保留旁观，不做中断与插入。** 否决。属主要的就是能从浏览器抢过方向盘——停掉跑飞的
turn、继续打字。只旁观会让手机发起的会话在电脑上无法操控，而那恰恰是网页席位存在的理由。

**POST 继续回流事件，*同时*再加一条订阅。** 否决。两条事件路径，冗余。单一订阅让发送方
不再是特例，并消掉一类竞态；重放缓冲覆盖了发送方的早期事件。

**把所有待处理消息合并成下一个 turn。** 否决，留作一行开关。串行 FIFO 是可预期的默认；
合并（agent 上下文更完整、turn 更少）等到返工噪音真的让人烦时再议。

**跨重启持久化待处理队列。** 否决。守护进程重启很少见，丢掉尚未提交的消息与
「进行中的 turn 在重启时被标记失败」是一致的。把它们作为 queued 行持久化是以后的加固项。

**干脆删掉这个页面。** 2026-09-10 真的这么做了，也正是这份记录消失两天的原因——见下。
