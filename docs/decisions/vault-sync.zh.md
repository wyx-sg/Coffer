# 仓库多机同步

> English: [vault-sync.md](./vault-sync.md)

- **状态：** 已采纳
- **Spec：** [vault-sync](../../specs/vault-sync/spec.md)
- **章程：** 原则 1（0.6.0——与用户自有的同步远端做双向收敛）

## 背景

Coffer 是本地优先的：每台机器拥有自己的仓库，没有任何厂商云端充当事实记录方。
一个开发者在笔记本和台式机上做同一个项目，两台机器都会产生仓库状态——知识文件、
skill、MCP 注册、agent 配置、凭据——他需要的是一个仓库，而不是两个。

这个决策已经做过四次，而这段历史如实讲出来，本身就是当前答案的论据。

- **0.3.0——持续同步。** 第一个答案是基于用户自有 git 仓库的收敛，而且真的建成了：
  机器身份、带 TTL 的墓碑（以免删除被复活）、对竞争编辑做时间戳仲裁、对导入失败的
  资源做隔离重试、一个 git 工作树，以及一个后台 worker。
- **0.4.0——移除。** 这套机制占了 sync 切片的大半，而且没有立住。2026-07-10，两台
  跑着不同构建的机器互相删掉了对方的 skill、记忆和资源：导出是破坏性的——它清空
  整棵树再从本地状态重写——而且它在这台机器完成首次导入之前就跑了，于是「我从来
  没有过这个」和「我删掉了这个」在交给 git 的 diff 里长得一模一样。同一起事故里还有
  第二个故障：一台机器重新导出了一个几个月前的、已成孤儿的凭据密文，仅仅因为它同步
  得最晚就赢下了合并——因为删除资源时留下的凭据行没有被清掉，之后每一次导出都会把
  它重新播撒回去。例外被撤回，功能被削减为导出与导入。
- **0.5.0——单向备份。** 导出与导入回答了「把我的仓库搬到另一台机器」，但没有回答
  「我的磁盘坏了」或「把我上周删掉的东西找回来」。于是 Coffer 有了一个备份远端：
  一个 worker 定时把仓库导出进 git 工作树，提交，推送。它从不拉取。没有任何东西
  需要仲裁，因为没有任何东西在收敛。
- **0.6.0——双向收敛。** 单向备份让两台机器各自漂移，而 Coffer 既不会察觉也不会
  调和；导出/导入只能靠手工补这个缺口，也就意味着补得不够勤。现在 Coffer 与用户
  自有的远端做收敛：既推送本机改了什么，也把远端带来的东西应用回来。

### 为什么 0.4.0 判为太贵的那套机制现在负担得起

0.4.0 撤回例外，是因为收敛要付六样东西：机器身份、带 TTL 的墓碑、冲突仲裁、
隔离重试、一个 git 工作区，以及一个后台 worker。

其中两样已经建成、也已经付过钱了。0.5.0 的备份远端为了它自己就需要 git 工作区
和定时 worker，它们今天就在代码树里。

另外四样之所以贵，只有一个原因：仓库的主体内容是一个被投影成文件的**数据库**。
git 看到的树是 SQLite 的一层渲染，而不是仓库真正编辑的那个东西，所以 git 算出来的
diff 并不是仓库做出的 diff——收敛所需的每一条保证，都必须在 git 之外、在 Coffer
自己的代码里、对着一个可能与其源头不一致的投影重新建立一遍。

自从[知识层变成一个文件目录](knowledge-is-plain-files.zh.md)以后，主体内容**就是**
这些文件，留在 SQLite 里的只剩下几十份小而确定性序列化的文档。于是那四样各自坍缩：

| 0.4.0 的代价 | 0.6.0 的形态 |
| --- | --- |
| 带 TTL 的墓碑 | 溶解进 git 自己的树——删除在提交图里就是删除，共同基点把它与「从来没有过」区分开 |
| 用于仲裁的机器身份 | 坍缩成一个本地指针，指向本仓库确实吸收过的最后一个提交；它从不外传 |
| 冲突仲裁 | 坍缩成 `git merge` |
| 隔离重试 | 坍缩成一组导出器不得删除的路径 |

## 决策

Coffer 与用户自有的**一个** git 仓库做收敛。一个后台 worker 跑一轮：把仓库序列化
进工作树并提交，把远端合并进这个提交，把由此得到的差异应用回仓库，推送。远端是
会合点，绝不是事实记录方——每台机器的仓库都保持完整，所以远端可以被删掉，再从
任意一台机器重建。

### 仲裁者是 git 的三方合并

Coffer 不写自己的仲裁。两台机器改同一份文档的不同部分是常态，git 不用帮忙就能
合并；同一块被改了两次才是真冲突，就按真冲突处理。时间戳仲裁是 0.3.0 的答案，
也正是它让一个几个月前的密文靠同步得最晚而获胜：「提交更新」说的是一台机器什么
时候跑过，不是用户想表达什么。

有两条很窄的规则挨着合并放，而不是取代它。凭据密文永远不进文本合并——Fernet
token 在明文里带着自己的加密时间，所以同一个 ref 的两份密文不需要密钥就能排序，
加密更新的那份胜出。另外，当配置了内部模型时，一个有界的 agent 过程可以**只在
工作树里**尝试处理剩下的冲突，并且必须过校验门。没有模型、或者校验门没过，这一轮
就停下，由用户用自己的 git 工具解决；仓库不被触碰，指针不动。

### 本地状态在合并之前提交

顺序就是决策本身。先拉再应用会丢掉本地编辑：树停在指针上、什么都没提交时，fetch
会快进，git 根本没有机会做三方合并，远端那一版会直接覆盖仓库在同一路径上的改动。

先提交本地状态，才给了 git 它需要的三个输入——基点、本地、远端。那一刻仓库等于
本地提交，所以从本地到合并结果的 diff 恰好只包含远端贡献的那部分，把它应用上去，
仓库就落在合并结果上，而本地编辑原封不动。

### 应用的是相对指针的差异，不是整体覆盖

指针是本仓库确实吸收过的那个提交。它存在本地，从不外传，只有当一轮的改动真的被
应用时才前进。这一轮应用的一切，都是相对它表达的。

这正是删除之所以安全的原因。只有当删除作为删除出现在 diff 里时才会被应用，而它
之所以能出现在那里，只可能是某台机器相对共同基点真的移除了那份文档。仅仅是**没有**
某份文档的机器，相对自己的基点没有做任何改动，而 git 把「未改动」当作对什么都没有
断言。这就是 0.3.0 给不出的保证。

有两条规则守着这个 diff 的诚实性，它们在 spec 里是规范性的：导出器差分地写，绝不
清空再重写一个目录；导出器绝不删除重试集合里的路径——本仓库没能吸收的文档是待处理，
不是被删除。

因为应用是无人值守跑的，有两道护栏为它的缺陷兜底。应用前快照打在本地提交处，
于是回滚就是同一套机制倒着跑。而断路器会在一轮的删除超过配置份额时停下来问用户——
并且是**双向的**：它既守着这一轮要应用进仓库的东西，也同样守着这一轮自己的导出
要作为删除**发布**出去的东西。第二个方向在「受损的是本机」时才是关键：一个因为重装、
恢复失败或一次误手 `rm -rf` 而丢了文件的仓库，否则就会把这场损失当作普通删除发布
出去，把其他机器一起拖下水。

### 加入一个远端是两种情况，而分清它们正是这里的决策

没有指针的机器就是在加入，而加入者有两种，需要相反的处理方式。远端的注册表要么
持有这台机器的 id，要么没有——决定权就在这里：

- **新机器取并集。** 它的 id 不在注册表里，于是指针是 git 的空树，diff 是从「无」
  出发的 diff，只可能包含新增。这台机器拿走远端持有的一切，并保留它本来就有的
  一切。在这里删除是结构上不可能，而不只是被规避掉了。
- **归来的机器恢复自己的基点。** 它的 id 在注册表里，说明它此前收敛过，而它的
  描述文件记着它当时到达的那个提交。那个提交成为指针，这一轮就是一次普通的
  「陈旧机器」轮次：合并接受远端的删除，保留本机的编辑，什么都不会复活。

把归来的机器当成新机器，看上去是保守的默认选项——并集什么都不删——而它其实是一个
数据丢失缺陷。一台重装了 Coffer 的机器保留着自己的仓库文件，却丢了指针；以「新机器」
身份重新加入时，它会把其他机器在它缺席期间删掉的一切重新发布出去。所有删除被一次性
撤销，而且不会引发任何冲突，因为并集没有基点可供分歧。

镜像的那一面，正是发布侧断路器存在的理由。一台 `~/.coffer` 被抹掉的归来机器，拥有
一个有效的、恢复出来的基点和一个空仓库，而合并会把这读成「这台机器删掉了一切」——
2026-07-10 的形状，从另一个方向到达。Coffer 分不清被抹掉的磁盘和一次刻意的清空，
所以它不猜：这一轮停下来发问。

这个识别是「任何以没有指针开始的轮次」的性质，而不是 `adopt` 命令的性质，所以在一台
忘了自己指针的机器上配置远端，绕不过它。无论是哪一种情况，加入都是一次显式且被
如实报告的行为：在应用任何东西之前，界面会说清这是哪一种情况、以及它将搬动什么。

### 本地导出与导入被删除

把一个 bundle 写进目录、再读回来，是一次没有基点的整体覆盖。它正是造成 2026-07-10
事故的那个操作，而且无法与基于 diff 的应用共存：留着它，就等于留着一条受支持的
路径，让一台陈旧的机器悄悄覆盖一个新鲜的仓库——而这恰恰是指针存在的意义。

它服务过的需求不靠它也能满足。新机器跑 `coffer sync adopt`。离线介质就是 U 盘上的
一个 `file://` 远端。把副本交给别人就是 `git clone ~/.coffer/sync`。这些都各有基点；
bundle 没有。

### 机器身份由主机派生，名字是可变的标签

`machine_id` 是一个键：它命名机器的描述文件，是资源 `scope.machines` 引用的东西，
并且必须扛过重装 Coffer。一台以新身份回来的机器会变成幽灵——所有按旧身份限定的
东西都会静悄悄失效，还没有任何报错来解释。所以这个 id 由主机派生（macOS 用
`IOPlatformUUID`，Linux 用 `/etc/machine-id`，只有兜底时才用存下来的 UUID），
而不是由 Coffer 生成；外传的是它的加盐哈希，绝不是原始硬件标识符。

支持「派生」的最强论据就是上面那一条：只有一个扛得过重装 Coffer 的 id，才能把
**归来的**机器和**新的**机器区分开。生成式的 id 会让重装过的机器变得认不出来，
让每一次重新加入都成为并集，让机群在它缺席期间做过的每一次删除都回来。派生身份
不是为了 scope 选择列表的锦上添花，它正是「加入」之所以安全的原因。

`machine_name` 恰好相反：由用户选定，随时可改且代价为零，存在这台机器自己的描述
文件里。重命名一台机器不可能弄坏任何 scope，因为没有任何 scope 引用名字。

### 机器注册表是派生视图，不是被同步的表

每台机器恰好写一份文档——`machines/<machine_id>.yaml`——并且不写任何别的机器的。
因为每台机器拥有互不相交的路径，这些文档不可能冲突，git 合并它们毫不费力。注册表
就是 `machines/*.yaml` 当下的内容。

描述文件还会发布这台机器的指针——它最后吸收的那个提交。指针本身从不作为算法的
共享输入外传；发布出去的只是一份「这台机器走到了哪里」的记录，好让这台机器在自己
忘记时能把基点找回来。归来的加入者读的正是这个字段。

被同步的注册**表**则相反：每台机器都写每一行，于是这份唯一职责就是描述机群的状态，
反而成了树里争用最激烈的东西。0.4.0 删掉了那张表，它不会回来。心跳字段每个日历日
最多重新打一次戳，所以一台空闲的机器不会每轮都提交噪音；界面上说的是「最后收敛的
那一天」，而不是暗示一个它并不拥有的时间戳。

### 无人值守改写同步内容的组件要指定一台归属机器

一个没有人审阅 diff 就改写仓库内容的 worker，在一台机器上是安全的，在多台机器上
就不安全。知识的整理（tidy）过程就是今天已经存在的这种情况：同一份语料在两台机器
上各跑一遍，两边都把同样的两篇笔记并进一份主题文档——但并进的是**不同的**文档。
合并干干净净（两边都认为那两篇笔记被删除，两份主题文档是不同路径上的新增），而
仓库最后把同一份知识存了两遍。git 看不见这件事，因为什么都没有冲突。

所以这类改写组件要指定一台归属机器，在其他任何机器上都是空操作。tidy 本来就默认
关闭且按安装维度生效，所以这只多出一个字段，而不是多出一个概念；「归属机器关着，
于是不做 tidy」对一个后台的锦上添花功能来说是正确的取舍。改写过程与收敛轮次还共用
同一把锁——在改写途中取的导出是一张撕裂的快照；而「删除对编辑」朝编辑一侧解决，
因为编辑是某个人或某个 agent 刚刚做出的决定，而删除是一次整理判断，下一轮还会再做
一次。保留（retention）worker 完全不需要这些：它清理审计日志、MCP 调用记录和会话，
这些都不同步。

## 已考虑的备选方案

- **把文件树交给用户自己的 git，只同步结构化状态**——否决。如果拉取由 Coffer 来跑，
  那无论如何都是收敛，同样需要这条修正；如果由用户来跑，那 Coffer 根本没有在同步，
  它本要解决的漂移依旧存在。它还会从 `skill` 中间切一刀——文件与注册行是同一个东西
  的两个面——让半个资源留在边界的另一侧。
- **原样恢复 0.3.0 的那套机制**——否决。它是为了收敛一个被投影成文件的数据库而建的，
  而那个数据库已经不再持有主体内容。今天重建墓碑、仲裁和隔离，等于在 git 之外重新
  实现四件 git 已经会做的事，还会把制造了 2026-07-10 事故的那道投影缝隙一并带过来。
- **由 Coffer 托管的同步服务端**——体验最好，但那是厂商控制的事实记录方；否决，
  并且明确在 0.6.0 例外之外。它需要一条宽得多的章程修正。
- **整体拷贝 `~/.coffer/`**——最简单，但它会把机器本地状态（daemon 配置、端口分配、
  每台机器自己的日志）和一个无法合并、无法查看、无法部分应用的二进制 SQLite 文件
  一起带走；否决。这也是确定性文本序列化的由来——正是它让一轮无话可说的收敛不产生
  任何提交。

## 影响

- `sync/` 切片保留它的序列化器、路径可移植性与凭据密文处理，并新增收敛轮次：存在
  本地的指针与重试集合、按文档种类分派的差分应用器、应用前快照与断路器。0.5.0 的
  git 工作区与定时 worker 是复用，不是重建。
- 资源 `scope` 重新长出机器维度——两个互相独立、以 `AND` 相连的列表，各自为 `null`
  表示不限。既有行以「增加字段」的方式迁移，因为 `machines: null` 精确复现今天的行为。
- Coffer 现在会在没有人在环的情况下写仓库。这是本决策真正的代价，也正是指针、快照
  和断路器之所以是规范性要求而非可选优点的原因。
- 一个冲突会在两台机器上同时阻塞收敛，直到有人解决它。这是有意的：两台机器就一份
  文档悄悄各执一词，比两台机器一起等着更糟。
- 序列化器的确定性以一种新的方式成为承重件。在备份下，它让 diff 可读；在收敛下，
  一个非确定性字段就是每一轮都会出现的伪冲突。
- 远端需要一个推送凭据，在推送时解析，绝不写进 `.git/config`，绝不出现在命令行上。
  凭据密文只在用户选择开启时随行，主密钥仍然走带外引导。
- 会话、审计日志与 MCP 调用记录保持机器本地。它们记录的是*在某台机器上*发生了什么；
  合并它们是另一个功能，形态也不同。
