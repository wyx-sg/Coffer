## 背景

2026-09-09 到 2026-09-14 之间，项目删掉了五项能力，然后又把每一项都放了回来：

| 能力 | 删除 | 恢复 |
| --- | --- | --- |
| 桌面壳 | 退役，改由 daemon 提供 Web UI（#317，2026-09-09） | 架在共享前端之上恢复（#376，2026-09-13） |
| Web 端 Chat 页面 | 删除，并入 channels 规范（#322，2026-09-10） | 连同其 REST/SSE 接口面一起恢复（#370，2026-09-12） |
| 仓库同步 | 持续同步降级为导出/导入（#314，2026-09-09） | 先是单向 git 备份（#362，2026-09-12），再是双向收敛（#381，2026-09-14） |
| 记忆层 | 并入知识层成为一个 kind（#321，2026-09-10） | 重新拆出为独立 kind（#379，2026-09-13） |
| Activity 页面 | 审计缩减为一部分事件和一个读取器（#325、#331，2026-09-10） | Coffer 保有的三种记录各自一个 tab（#377，2026-09-13） |

检索在一天之内走了同样的弧线：架在 embedding sidecar 之上的带排序语义检索随知识层精简一起被删（#368，2026-09-12），当天恢复，又再次删除（#382，2026-09-14）。

每一次反转都付了两遍钱。章程五天里修订了三次（0.4.0 删掉同步例外，0.5.0 加回一个更窄的，0.6.0 又换掉它）。迁移在删除时和恢复时都重写了用户数据（`0066` 删掉十一张知识表，`0076` 与 `0077` 分别收拾生效范围与 embedding 变更留下的残局）。ADR 被删掉又重建，规范章节被砍掉又重写，路线图的状态单元格长成了几千字的修订日志——因为每一条都得先解释上一次反转，才能说清当前状态。

每一次删除背后的模式都一样：只按能力自身的维护成本来评判它，而没有称量它当初被建出来的理由——然后真实使用在几天之内就把那个理由摆了出来。壳因为每次更新的成本退役，又因为「够得着」的成本恢复；Chat 页面因为每条会话都来自 channel 被删，又因为「在桌面上看着一段手机驱动的会话」是任何 channel 都做不到的事而恢复；同步为了躲开收敛机制被降级，又因为两台机器生产同一个仓库正是这个产品本身而恢复。

唯一*不*在那张表里的删除——语义检索——出于另一个原因，需要单独说清楚，因为[知识层是一个文件目录](knowledge-is-plain-files.zh.md)把它的代价记得如此仔细，读者可能把这次删除当成终局。

## 决策

**五项能力是已定的产品范围。** 它们不是删除的候选；提议删除其中任何一项，就是提议修订本 ADR，由项目所有者裁决：

1. **桌面壳**——spec mcp-gateway FR-029 – FR-032，[桌面壳回归](desktop-shell-over-a-shared-frontend.zh.md)。
2. **Web 端 Chat 页面**——spec channels FR-072 – FR-078，[Chat 是单属主的实时镜像](chat-single-owner-live-mirror.zh.md)。
3. **与用户自有远端的双向仓库同步**——spec vault-sync，[Vault Sync](vault-sync.zh.md)，章程 0.6.0。
4. **Activity 页面**——审计日志、MCP 调用日志与 daemon 日志，各自一个 tab（spec ui-shell；这些记录本身属于 spec mcp-gateway）。
5. **知识层与记忆层，作为两个 kind**——spec knowledge 与 memory，[知识层是一个文件目录](knowledge-is-plain-files.zh.md)，[聚合 agent 的记忆](aggregate-agent-memory-never-write-it.zh.md)。

**字面检索是占位，不是裁决。** 知识与记忆的检索是能作答的最简单做法——机器上有 ripgrep 就用它，没有就走语义完全一致的内置 Python 遍历——原因是知识与记忆的*设计*尚未定型，而建在未定型设计上的索引，正是 2026-09-12 那次审计发现无人使用的东西。语义检索（embedding、排序）预期会在设计定型后回归，并遵守「知识层是一个文件目录」已经定下的约束：文件仍是唯一的事实来源，任何索引都是仓库之外的可丢弃 sidecar。本仓库中没有任何内容应被读作「我们决定不做语义检索」。

**删除一项能力必须说明反转代价。** 删除任何能力的 PR——上述五项走修订本 ADR，其余走普通评审——MUST 在描述中写明反转一次要付出什么：它删掉的代码、它对用户数据执行的迁移及能否撤销、它改写的文档（规范、ADR、章程、路线图）。它 MUST 在同一个 PR 里删掉死代码与每一处文档引用，使代码树里永远不会留下一项半删除的、要靠下一位读者去重建的能力。

## 后果

- 五项能力的 ADR 保持 `Accepted`，其规范留在路线图的进行中表格里。它们的维护成本——Rust 壳、同步 worker 及其护栏、两个检索面、三个日志读取器——被接受为产品本身的成本，而不是要靠删除来偿还的债务。
- 路线图的状态单元格只描述当前状态；它们过去承载的历史移入路线图的 `## 修订日志`，每份规范一个小节，按时间顺序。一个以解释某次反转开头的状态单元格，就是本 ADR 要杜绝的气味。
- 语义检索回归时经由知识与记忆规范进入——新增 FR，而不是新 ADR——字面检索留作索引缺失时仍能作答的兜底，与 2026-09-12 那次恢复的做法完全一致。
- 没有写明反转代价的删除 PR 是不完整的，会被退回——和缺 `.zh.md` 伴生文件的 PR 一样。

## 备选方案

- **继续逐 PR 决定。** 否决：正是这个流程在六天里产出了六次反转。每个 PR 都从它看得见的成本出发论证得很好。
- **给有争议的能力加 feature flag。** 否决，且章程 0.4.0 已因同一理由否决过：关掉的路径仍要维护和测试，而一项没人够得着的能力不是产品范围，是带开关的死代码。
- **宣布语义检索永久出局。** 否决：2026-09-14 的删除记下了实打实的损失——用调用方自己的话提问，不再能找到一个有辨识度的短语找得到的东西——而它输掉的原因是底下未定型的设计，不是这个想法本身。在设计定型之前下裁决，会是上述五个错误在下一层的重演。
