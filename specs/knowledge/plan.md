# Implementation Plan: Knowledge Layer

> 中文版: [plan.zh.md](./plan.zh.md)

**Spec**: [./spec.md](./spec.md)
**ADR**: [Knowledge Is Plain Files](../../docs/decisions/knowledge-is-plain-files.md)
**Status**: Accepted — reduced to plain files 2026-09-12

**Folder name**: this spec lives at `specs/knowledge/`, the spec id every
inbound link and `scripts/audit_acceptance.py` keys on.

## Summary

The knowledge layer is a **directory of Markdown files**, not an index over
them. `~/.coffer/knowledge/<collection>/…` is the sole source of truth: nothing
is chunked, embedded, tokenized or reconciled, so a file the user edits in their
own editor is live on the agent's very next call. A **collection** is a
top-level folder and one `knowledge` Resource, created deliberately, and it
exists so the framework's per-agent scope can authorize it. Retrieval is a
catalogue generated by walking the tree at call time, plus ripgrep. Five MCP
tools: `list`, `grep`, `read`, `write`, `delete`.

This replaces ~10,800 lines of backend across three layers, eleven database
tables, two storage lanes, three kinds of scope, four retrieval modes and an
any-format ingestion pipeline — a stack the 2026-09-12 audit found had largely
never executed. The evidence and the reasoning are in the ADR; this document
describes what is built.

## Technical Context

| Dimension | Value |
| --- | --- |
| **Language / Version** | Python 3.12+, TypeScript 5.x |
| **Primary dependencies added by this spec** | `PyYAML` (frontmatter), and `ripgrep` on `PATH`. Nothing else — no index, embedding or conversion library (FR-080). |
| **Storage** | Markdown files under `~/.coffer/knowledge/<collection>/`. **No database table** (FR-081): a collection is a row in the kind-agnostic `resources` table like every other Resource. |
| **Testing** | 4-tier model with acceptance markers. No fake embedding provider is needed, because nothing embeds. |
| **Constraints** | Path construction confined to one module; hidden entries unaddressable; no module may import an index, embedding or conversion library. |
| **Scale** | Single user; a corpus small enough that a catalogue fits in an agent's context (the live corpus is 51 files). |

## Constitution Check

Standard layer rules. The domain holds value objects that describe what is on
disk and nothing that describes a row; the application holds one service, the
five tools, the tidy pass and the skill seed; infrastructure owns paths, the
file tree, frontmatter and the ripgrep adapter. PyYAML lives only in
`infrastructure/knowledge/frontmatter.py`, and path construction only in
`infrastructure/knowledge/paths.py`.

## Surfaces

- **MCP — five tools**: `list`, `grep`, `read`, `write`, `delete`. None takes a
  `scope`, a `mode`, a `top_k` or a `cwd`; a call spans every collection the
  session's agent identity is authorized for (FR-012, FR-024).
- **HTTP — eight routes** under `/api/v1/knowledge`: list and create
  collections, `GET /tree`, `GET`/`PUT`/`DELETE /file`, `GET /grep`, and
  `POST /collections/{name}/tidy`. Deleting a collection goes through
  `DELETE /api/v1/resources/knowledge/{name}` — a collection's lifecycle is a
  Resource's. See [`contracts/api.openapi.yaml`](./contracts/api.openapi.yaml).
- **CLI — eight commands**: `collections`, `create`, `ls`, `read`, `write`,
  `delete`, `grep`, `organize`.
- **UI**: one tree, read-only preview, open-in-editor and reveal on a file and
  its folder ([Daemon Proxies File Actions](../../docs/decisions/daemon-proxies-os-file-actions.md)).
- **Delivery**: the `coffer-knowledge` skill, seeded into Coffer's own skill
  store at boot and delivered through the existing skill channel (spec
  [skill-manager](../skill-manager/spec.md)). Idempotent — the bundled folder is
  re-imported every boot, so an edit ships with the next daemon start and a
  user who deleted the skill gets it back. No hook, no session injection, no
  write into any agent's memory files (FR-042).

## Tidy

One bounded agentic pass over one collection, driven by the internal-engine
connection, whose tool surface is the same five operations. It copies a file's
prior revision into `.history/` before any overwrite, and with no index behind
it there is nothing to reconcile afterwards. With no internal connection it is a
clean no-op (`status: no_model`).

`TidyWorker` is shaped like `RetentionWorker` — a catch-up pass shortly after
boot, then on an interval, a failing pass logged without killing the loop — but
it consults one installation-wide flag, `auto_tidy_enabled` on
`internal_engine_config`, **default false**. That default is the point rather
than caution: the pass rewrites files a human and an agent manage together with
no diff to approve, so an unattended rewriter should be something the operator
switched on, never something they discover running (FR-051).

## Migration

One revision, `0066_knowledge_is_plain_files`, and **the order is the whole
point**. A document's title lived only in `documents.title`, so `upgrade` runs
the on-disk rewrite first — reading the rows it is about to destroy — and only
then drops eleven tables, each drop guarded so a database missing any of them
still upgrades (FR-070, FR-071). `downgrade` raises: the ULID names and the
`.raw/` copies cannot be reconstructed, and no compatibility shim is left behind
anywhere. Details in [`data-model.md`](./data-model.md).

## Risks and accepted trade-offs

| Risk | Position |
| --- | --- |
| **No semantic matching.** `grep` matches literal text only; conceptual recall now depends on the agent reading the catalogue and judging relevance. | Accepted, with a ceiling: it works while the catalogue fits in context — roughly 40 tokens an entry, so hundreds of files are comfortable and thousands are not. Past that the answer is a real semantic stack built for that need, not the one removed here, which was never configured. |
| **Tidy rewrites a jointly managed artifact with no review step.** Nothing diffs the output before it lands. | `.history/` is the entire safety net, and the worker ships off by default so the human stays in the loop until they decide otherwise. |
| **Ranking is the agent's problem.** A broad grep over a large corpus returns many matches. | The catalogue keeps it tractable, which puts real weight on file names and `description` lines — hence `description` being required. |
| **Migration is destructive and one-way.** | Deliberate. Titles are written into file names and frontmatter *before* the tables are dropped; there is no second chance and no shim. |
| **Per-agent authorization is a convention, not a security boundary.** An agent with shell tools can read any file under the root. | Stated as such on every surface (FR-014). Real isolation would need a separate vault or filesystem permissions, and is out of scope. |
| **Whether a delivered skill actually makes agents reach for the layer is unproven.** Tool descriptions demonstrably did not. | It is a hypothesis with evidence behind it — fifteen `coffer-*` skills are natively discovered today — and it is cheap to verify: the invocation log already records every knowledge call, so a week of ordinary work answers it with no new instrumentation. |

## Out of scope

- Any derived index: chunking, FTS5, vectors, embeddings, hybrid fusion,
  reindex, lazy reindex-on-read.
- Any ingestion surface: upload, format conversion, converter registry,
  `.raw/` provenance, external source tracking, re-conversion locks.
- Any derived boundary: cwd-resolved scopes, auto-provisioning,
  `project-<ULID>` naming, git-root resolution.
- An in-app editor. The UI renders; the user's own editor edits.
- Reranking, HyDE, multi-query or LLM synthesis at read time — the agent
  synthesizes.
- A filesystem watcher. Nothing is derived, so there is nothing to invalidate.
- Multi-machine convergence (constitutional; the vault-export-import spec covers
  export, import and one-way backup).
