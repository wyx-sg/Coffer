# 事件流 {#the-event-stream}

Web 界面显示的状态会在它背后发生变化：智能体改了某个服务器的文件，一轮调和修好了某个智能体的配置，一轮同步从另一台机器导入了一个技能，某个 MCP 服务器开始出错。页面必须知道这些。本页讲 Coffer 为此用的机制：整个守护进程只有一条流，它只说*什么*变了，从不说*怎么*变的。决策本身和权衡过的方案见决策记录 [The Wire Contract Is Generated From the Pydantic Models](https://github.com/wyx-sg/Coffer/blob/main/docs/decisions/wire-contract-generated-from-the-pydantic-models.md)（事件流一节）。

## 只给提示，不给状态 {#hints-not-state}

流上的每个事件都是一个很小的信封：一个序号、变化的东西属于哪种类型、是哪一个、它现在的修订号，以及它是被写入还是被删除。仅此而已，不带这个东西的任何字段。

客户端收到事件后，让自己为这个东西缓存的内容失效，再通过普通 API 重新取一次。这是有意为之。如果流里带着新状态，它就成了每种资源的第二份描述，有自己的结构、自己的脱敏规则、自己的顺序保证，而且必须永远和 REST API 保持一致。作为一串提示，它不可能和任何东西不一致：REST API 仍是读取状态的唯一入口，流只负责告诉你什么时候该重新读。

同样的性质让丢事件在最坏情况下也无害。漏掉提示的客户端会显示旧数据，直到下次重新获取；它永远不会显示流凭空编出来的错误数据。

## 提示从哪里来 {#where-the-hints-come-from}

对资源的每一次写入——不管来自 Web 界面、智能体的 MCP 调用还是同步导入——都会经过资源框架，而资源框架本来就会把写入通知给[调和器](/zh/architecture/reconciler)，好让下一轮来得早一点。事件流就在同一个地方监听。没有哪种类型需要记得通报自己的写入，所以也没有哪种类型会忘记。

唯一不是资源写入的，是总览页上的「需要你处理」列表。它是按需从各类型自己的信号算出来的——测试失败的服务器、未连接的智能体、因冲突停下的同步——没有任何东西记录它变化的时刻。所以守护进程会盯着它：在资源写入之后、每轮调和之后，以及按一个较慢的定时器，重新计算这个列表的指纹，只有指纹变了才通报一次 `attention` 变化。指纹只覆盖有哪些条目、严重程度如何，不包括措辞，所以改一句提示文字不会把每个页面都叫醒。

## 编号、重放与重新同步 {#numbering-replay-and-resync}

每个信封都拿到序列中的下一个编号，这个序列在守护进程每次启动时从 1 开始。守护进程在内存里保留最近的大约一千个信封。

连接会断：笔记本休眠、桌面应用重新加载、守护进程重启。客户端重连时会说出它看到的最后一个事件，和任何 Server-Sent Events 客户端的做法一样；守护进程先把它仍保留着的、在那之后的所有事件重放一遍，然后再转为实时推送。短暂断开不会丢任何东西。由于编号每次启动都从头开始，事件的 id 同时标明了守护进程的这一次运行和编号，所以重启前的「事件 5」永远不会被当成这次运行的事件 5。

如果断开太久——编号比守护进程还保留的任何事件都旧，或者它指向的事件是这次运行从没发出过的（因为中间守护进程重启过）——重放就不可能完整。守护进程不会只重放一部分、让客户端误以为自己已经是最新的，而是先发一个 `resync` 事件。它的意思是「你可能漏掉了些东西」：客户端重新获取它显示的所有内容，然后照常跟着实时流走。

同一条规则也保护守护进程不被慢读者拖垮。每个连接只能积压有限数量的未投递事件。落后更多的客户端会丢掉积压，改为收到一个 `resync`，所以一个卡住的标签页不会让守护进程的内存一直涨。

## 让连接保持可信 {#keeping-the-connection-honest}

没有变化时，流按固定间隔发送 `heartbeat` 事件，带上最新的序号。收不到心跳的客户端就知道连接已经死了，而不只是安静，于是重连。心跳也能让刚重连的客户端知道自己是否落后。

## 在页面里读取 {#reading-it-from-a-page}

这条流和其他所有管理调用一样，用同一个令牌把关。浏览器内置的 `EventSource` 不能发自定义请求头，所以页面用 `fetch` 读流、自己解析事件——和它读取对话实时输出的方式一样。对话流仍然是分开的：它承载一个轮次的内容，那是状态，不是提示。

显示实时状态的页面在打开期间跟随这条流：总览页是这样，所以一条「需要你处理」在问题解决后马上消失；活动页也是。读取器在 Web 界面里只有一处实现，并且会自己保持连接：连接结束后等一会儿，带着它看到的最后一个变化的 id 重连；每被拒绝一次就多等一会儿，所以守护进程宕着时，代价是每几秒一个请求，而不是一个死循环。每收到一个 `change`，它让该类型相关的缓存列表失效；收到 `resync` 就让全部失效；然后由页面自己的查询通过类型化端点重新获取。

Web 界面显示的列表中有两个不在流上，因为它们都不是资源：审计日志和 MCP 调用日志。所以活动页每隔几秒重新读一次它们各自的最新一页——几行，而不是整个列表——另外每收到一个 `change` 也会重读审计日志的最新一页，因为资源写入会留下一条审计记录。

## 页面可以不再做的事 {#what-pages-can-stop-doing}

有这条流之前，每个页面靠自己的定时器轮询来保持新鲜，间隔从五秒到一分钟不等，所以一个变化最多要一分钟才出现，而一个显示所有类型的页面就得轮询每一种类型。有了这一条流，变化一写入就出现，页面也只重新获取事件点名的那部分。

## 用游标翻页不断增长的列表 {#growing-lists-page-by-cursor}

页面收到提示后获取的列表，会以另一种形式遇到同样的问题：审计日志、MCP 调用日志、智能体的对话记录会话和对话列表，都会在有人翻页时继续增长。按位置翻页（「跳过前 50 条」）在顶部来了新行时会让后面每一页都错位，于是行在页与页之间重复或消失。这些列表改用一个不透明的游标翻页：每次应答都指明下一页从哪里开始，用的是列表排序中的一个位置而不是计数，这个位置不会因为前面插入了新行而移动。游标绑定在签发它的那个列表和那组筛选条件上；拿到别处使用会被直接拒绝，而不是去猜。
