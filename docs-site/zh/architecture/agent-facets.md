# 智能体切面 {#agent-facets}

Coffer 管理的编程智能体并不归它所有：目前是 Claude Code 和 Codex。Coffer 做的几乎每件事最终都落在其中一个上——写进其配置的 MCP 条目、链接到其技能目录的技能、投影到其设置里的模型提供商、把记忆交给它的 Hook、通过它驱动的一轮对话。本页说明 Coffer 如何把智能体之间的差异集中在一处，让支持一个新智能体，或把一种新资产放进已有智能体，变成一次添加而不是一次全局搜索。在写任何按智能体表现不同的代码之前，先读这一页。这个决定以及权衡过的备选方案记录在决策记录（ADR）[Agent Mechanisms Are Optional Facets on the Descriptor](https://github.com/wyx-sg/Coffer/blob/main/docs/decisions/agent-mechanisms-are-optional-facets-on-the-descriptor.md) 中。

## 问题 {#the-problem}

智能体之间有两类不同。

- **值。** 配置目录在哪里、哪个环境变量能挪动它、Coffer 可以显示和编辑哪些文件、哪个文件以什么格式保存 MCP 服务器、技能放在哪里、智能体以哪个程序运行。这些是关于某个产品的事实。
- **机制。** 模型提供商如何写进智能体的设置、Coffer 的会话 Hook 如何安装、智能体的原生记忆如何读取、如何在它上面运行一个轮次、如何判断它是否已安装。这些是行为。

值早就放在每个智能体一条的记录里了。机制却没有：每个机制都在自己的模块里问“这是哪个智能体？”。添加一个智能体，就得靠搜索找出每一处这样的提问，漏掉一处，只有等那个智能体走到那条路径时才会出错。更糟的是，有三处悄悄假定一种模型提供商协议恰好对应一个智能体——Anthropic 协议对应 Claude Code，OpenAI 协议对应 Codex——于是第二个讲同一协议的智能体根本无从存在。

## 思路 {#the-idea}

每个智能体一条记录，写明它的所有差异。值直接放在记录里。机制是**切面**：同一条记录上的可选槽位，要么填入一个实现，要么在智能体不具备该机制时留空。

共有四个切面：

| 切面 | 回答的问题 |
| --- | --- |
| 投影 | Coffer 能把哪些资产放进这个智能体、每项落在哪里，以及 Coffer 的资产如何翻译成智能体自己的形态。 |
| 驱动器 | Coffer 如何在这个智能体上运行一个轮次。 |
| 记忆读取器 | 如何以只读方式读取智能体的原生记忆。 |
| 依赖探测 | 智能体的程序是否装在本机，以及是哪个版本。 |

缺少的切面就是空的，每个使用方本来就会处理缺失的情况：没有投递 Hook 的智能体永远不会被提供 Hook，没有驱动器的智能体不会出现在对话的选择器里。

### 实现放在哪里 {#where-the-implementations-live}

记录本身是领域层里的纯数据。实现属于适配器层的工作——读文件、启动程序、调用 SDK——每个实现都归使用它的那部分 Coffer 所有：提供商翻译归提供商功能，投递 Hook 和记忆读取器归记忆功能，驱动器归对话，探测归智能体功能。所以记录只**声明**每个切面的类型，实现在组合根处**绑定**到记录上，组合根是唯一一个允许同时看到所有功能的地方。

绑定时从不说明哪个智能体是哪个。每个实现自己声明服务于哪个智能体，绑定器按这个声明分组。同一个智能体出现第二个实现，启动时就会被拒绝。组合根一次性构建出绑定好的目录，交给每个需要某种机制的服务；测试也构建同样的目录，只是把依赖探测换成固定答案，这样测试永远不依赖开发者碰巧装了什么。

## 投影是一个注册表 {#projection-is-one-registry}

投影是内容最多的切面，因为 Coffer 放进智能体的东西在不断增加。它是一个**按资产类型和落点索引的注册表**：

- **资产类型**是放进去的东西：MCP 条目、技能、模型提供商、投递 Hook——以后还有规则、命令、子智能体和权限；
- **落点**是它落在哪里：**用户级**（智能体自己的配置目录）、**项目级**（某个仓库内），或**共享**（多个智能体读取的目录，只写一次，只要还有读取方需要就保留）。目前两个已发布的智能体，所有条目都落在用户级。

每个条目都写明它落入的文件或目录——总是经过智能体的配置文件白名单，这是 Coffer 可写范围的安全边界——还写明从 Coffer 资产到智能体原生片段的翻译，以及一份能力声明。这份声明刻意保持很小：只包含已发布的智能体实际用到的内容。对模型提供商来说，它是智能体原生配置支持的传输协议，可能一个都没有。对投递 Hook 来说，它是 Hook 挂在哪个事件上。

这个注册表也是[调和器](/zh/architecture/reconciler)遍历的目标列表：新增一种资产类型，就是在能接收它的智能体上新增一个条目，而不是新增一个服务。

### 不靠协议映射的提供商投影 {#provider-projection-without-a-protocol-map}

模型提供商连接通过自己的作用范围到达智能体，而不是通过协议。每个智能体的提供商条目声明其原生配置支持哪些协议，没有任何地方把一种协议映射到某一个智能体。把智能体恢复为自带登录时，指定的是智能体，而不是协议。唯一还会出现协议的地方——旧版本写进 Claude Code 设置的 key helper 那一行——通过询问哪些智能体声明了该协议来处理。

提供商翻译是纯函数。它返回一份计划：主文件的新文本、在它之前要写的文件，以及在它之后要删的文件。原因在于 Codex 的模型目录：目录必须在设置指向它之前就存在，并且要一直保留到指向消失，这样智能体永远不会读到一个指向不存在文件的引用。同一个条目还能回答 Coffer 的键是否在位，启动检查就是靠它判断一个标为活动的连接其实并没有投影——向写入键的同一段代码提问，意味着检查永远不会和写入方产生偏移。

## 驱动器直接对接 {#drivers-are-direct}

Coffer 通过各厂商提供的结构化协议驱动每个智能体：Claude Code 通过它的 Agent SDK，Codex 通过它的 app server。通用的智能体协议只留给原生只讲这种协议的智能体；它从不替代直接驱动器，因为对这两个智能体来说，它只会在同一协议之上再加一层翻译，并把直接驱动器暴露的东西藏起来。对话功能在自己的依赖就绪后，请每个已绑定的驱动器各构建一次轮次提供器，所以对话选择器列出的恰好是有驱动器的智能体。

## 检测看两个信号 {#detection-has-two-signals}

仅凭配置目录，很难证明智能体已经安装。卸载后目录仍在，一次 dotfiles 检出也可能在从没装过该程序的机器上创建它。所以检测问两个问题：

1. **智能体的程序是否在它真正的 `PATH` 上，是哪个版本？** 守护进程自己的 `PATH` 往往是图形界面启动时拿到的截断版本，所以探测会向用户的登录 shell 询问智能体实际运行时的 `PATH`——这是一个操作系统层面的问题，由[平台端口](/zh/architecture/platform)回答——再把继承来的 `PATH` 合并在后面。然后在限定超时内向程序询问版本。版本参数不需要登录、网络或配置，答案按二进制文件缓存，所以升级能被察觉，而没变的二进制只问一次。
2. **配置目录是否存在？**

两者组合成一个状态：

| 程序 | 目录 | 状态 | 含义 |
| --- | --- | --- | --- |
| 找到 | 存在 | 已安装并在使用 | 可以添加和连接。 |
| 找到 | 不存在 | 已安装，从未运行 | 可以添加：在其标准目录注册时会创建该目录，里面只放 Coffer 需要的东西（它的 `skills` 目录）。 |
| 缺失 | 存在 | 仅剩配置 | 已卸载智能体留下的东西；显示为未安装，不能添加。 |
| 缺失 | 不存在 | 缺失 | 本机上完全没有这一类型。 |

每种类型只有一个智能体，并以类型命名（规格 agent-registry “Keep one agent per type, named by it”），所以检测按类型而不是按目录报告（规格 agent-registry “Report every supported type's detection state”）。每种支持的类型都有一行，无论是否已注册，包含它的状态、版本、它所在或将要注册的目录、它的标准目录，以及能否添加。对每种类型，发现过程只查看标准目录，以及守护进程环境中该类型自身环境变量（`CLAUDE_CONFIG_DIR`、`CODEX_HOME`）在已设置时所指的目录，别处都不看。第二个目录永远不会成为第二个候选：它作为该智能体的“使用其他配置目录”选项出现，或者在只有它存在时成为“添加”所注册的目录。一个未注册、但被任一信号看到的类型就是候选，每种类型最多一个。这些都不存储：每次显示智能体或候选时现读状态。

## Hook 会被读取，Coffer 自己的会被检查 {#hooks-are-read-and-coffer-s-own-is-checked}

智能体会运行来自自身设置文件和插件的 Hook，Coffer 也会安装一个自己的。Coffer 以只读方式读取所有这些 Hook：每个 Hook 的事件、matcher、命令以及声明它的文件。两个智能体保存 Hook 的格式相同，所以一个读取器就能同时服务两者；哪些文件带 Hook 是每个智能体记录上的一个值，每个已启用插件的 Hook 文件则通过插件列表找到。项目自己的设置不读，因为 Coffer 不知道智能体在哪些仓库里使用。

Coffer 自己的 Hook 通过标记找到，并按启动修复的方式检查：安装的命令与 Coffer 现在会写的完全一致即为最新，标记在但命令不同即为过期，不在即为缺失。最近一次触发时间来自审计日志，每次真实触发都会记在那里——“已安装”和“运行过”始终是两个不同的事实。

## 这条规则如何受保护 {#how-the-rule-is-protected}

整个设计所依赖的规则是：除了智能体记录和切面实现，其他地方都不问自己面对的是哪个智能体。一个构建门禁负责执行这条规则，它是 `make lint` 的一部分，因此也是每次 `make verify` 的一部分。

和平台门禁一样，它把源码当语法树来读，而不是当文本搜索。当允许范围之外的代码点名某个具体的智能体类型，或者把一个值与智能体类型的字面名称比较——也就是用字符串写出的同一种分支——时，构建就失败。用枚举从一个值构造成员，或者遍历所有智能体，都没有问题：两者都没有说明哪个智能体是哪个。允许的地方是：智能体记录及其领域、智能体功能自己的适配器、其他功能拥有的切面实现（每个都在门禁中按名称列出，在添加它的那次改动中加入），以及数据库迁移，因为那是历史。测试不扫描。

门禁失败时，会指出文件、行号以及它反对的内容。

## 出现新的智能体或资产时 {#when-a-new-agent-or-asset-appears}

- **新智能体**就是一种新的智能体类型：一条带着各项值的记录、它具备的切面实现，以及一份子规格。共享的切面契约测试——每个智能体的切面都必须遵守的一组承诺，针对每个智能体用一个假的配置目录运行——是新智能体在发布前证明自己合格的方式。
- **新资产类型**就是在每个能接收它的智能体上新增一个注册表条目，写明落点、翻译，以及已发布智能体所需的最小能力声明。
- **新机制**如果不适合任何现有切面，就是一次设计讨论，而不是加一个分支：它要么扩展某个切面，要么通过一份决策记录（ADR）争取成为新切面。
