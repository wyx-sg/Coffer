# 调和器 {#the-reconciler}

Coffer 承诺的很多东西，都是它并不拥有的文件的某种状态：它在每个智能体配置里的 MCP 条目、它交付的每个技能的链接、写在智能体设置里的模型提供商密钥、把记忆交给智能体的那个 Hook。这些文件会被智能体自己的命令行、其他工具、备份以及坐在键盘前的人改写——而且常常发生在 Coffer 没运行的时候。数据库说的是应该成立什么；只有文件说的才是实际成立什么。本页讲 Coffer 如何弥合这个差距。这个决定和当时权衡的选项见 ADR [One Level-Triggered Reconciler Converges What Coffer Writes Outside Its Database, Comparing Parameters](https://github.com/wyx-sg/Coffer/blob/main/docs/decisions/one-level-triggered-reconciler-compares-parameters.md)。

## 它依据的两条教训 {#two-lessons-it-is-built-on}

**存在不等于正确。** 有好几个月，一个已安装的记忆 Hook 一直在传一个命令行工具早已删掉的选项。每个会话一启动就报用法错误，而 Coffer 的状态却一直显示「已安装」，因为它靠标记识别自己的 Hook，从来不读参数。Coffer 自己的 MCP 条目也是同样的问题：一次升级挪走了启动器路径，或者条目写错了智能体，状态照样显示已安装。所以调和器用条目的全部参数来判断每一项。靠标记找到条目，是*定位*；比较它的参数，才是*判断它是否最新*。

**事件会漏掉两次事件之间发生的事。** 以前每种类型都按自己的一套触发条件检查自己那一部分——技能启用时、智能体注册时、启动时。在这些时刻之间发生的变化，或者守护进程停机期间的变化，会一直保持错误，直到下一个恰好覆盖它的触发。Coffer 里唯一从没有这个问题的部分，就是那个按定时器重新看一遍的部分。所以调和器是*电平触发*的：每一轮都比较完整状态，事件只是让下一轮来得更早。

## 目标 {#targets}

Coffer 保持成立的每一样东西都是一个**目标**。目标来自智能体的投射注册表（见[智能体切面](/zh/architecture/agent-facets)）：每个智能体能接收的资产——MCP 条目、技能链接、提供商投射、投递 Hook。一个目标回答三个问题，并执行一种写入：

1. **应该有什么？** 只根据 Coffer 自己的状态计算——它的数据行、每个资源的生效范围、当前构建的命令、启动器所在位置——得出一个条目列表，每个条目有稳定的键和它应有的全部参数。
2. **实际有什么？** 从文件中读取，解析成完全相同的形状，这样两边可以直接比较。解析很重要：其中好几个文件会被它们的所有者整体重写，按文本比较会看到毫无意义的差异。
3. **对差异可以做什么？** 由目标的**方向策略**决定（见下文）。
4. **写入。** 通过该类型自己的写入器进行，它只会碰 Coffer 自己标记的条目，原子写入，并保留原内容的备份。

一轮调和按键把期望条目和实际条目配对。缺失的期望条目是一次*新增*；没有谁期望的实际条目是一次*移除*；条目存在但有任一参数不同，是一次*修改*——这正是基于存在性的检查永远看不到的情况。

## 方向策略 {#direction-policy}

不是每个差异都可以靠写入来修复。每个目标针对每种差异说明：是**修复**、只**报告**，还是报告为**受阻**——原则上可修复，但现在不行。策略不修复的差异只报告，从不写入。

这些策略把曾经吃过亏才得出的判断固定下来，调和器让它们保持显式：

- **绝不覆盖别人的内容。** 如果有人在技能链接该在的位置放了一个目录，只报告，不替换。主文件夹缺失时，无法从它重新交付。
- **绝不凭过期的证据给智能体改道。** 如果智能体的记录显示它运行在某个提供商连接上，但智能体的设置里没有该连接的任何密钥，那么被纠正的是记录：该智能体的连接被清除，智能体继续用它自己的登录运行。把密钥写回去，会悄悄让某人的智能体走一个他们并没在用的网关。出于同样的原因，发现 Coffer 的密钥但背后没有连接时，只报告而不删除。
- **连接是人的行为。** Coffer 从不给一个没有 MCP 条目或记忆 Hook 的智能体添加它们；它只让已有的保持最新。已连接但缺少 Hook 的智能体会被报告为部分连接。
- **有些授权比另一些更强。** 少数差异在一种场合下可以修复，在另一种场合下只能报告。同步导入之后，导入的数据行携带着这个人在另一台机器上明确做出的开关操作，所以会写入（或移除）投射来跟随它。当一个人在偏移视图里应用某一项时，他们要求的正是那次写入。所以一轮调和知道自己*为什么*运行，策略可以读取这一点。
- **在原因消除前一直受阻。** 如果 MCP 条目必须指向的启动器找不到，就没有正确的条目可写，这个差异会被报告为受阻；无法解析的文件也一样。

## 一轮调和何时运行 {#when-a-pass-runs}

- **启动时**，在守护进程报告就绪之前——这一轮会修复它停机期间发生的所有偏移。
- **按周期**，每分钟一次。对两个已连接的智能体、二十个已交付的技能和一个活动提供商跑一整轮，实测不到三十毫秒，所以周期是按偏移可以在多长时间内不被察觉来定的，而不是按成本。超过两秒的一轮会记日志，因为那意味着某个目标做得太多了。
- **写入之后提前运行。** 任何界面对资源数据行的每一次写入，都会广播类型、资源和它的新修订号——一个每次写入都会递增的整数。广播唤醒循环，循环等半秒收集相邻的写入，然后对跟随该类型的目标跑一轮。广播只是加速器：即使丢了一次，变化也会在下一次周期性调和时被发现。
- **对人自己的写入立即运行。** 当有人启用技能、缩小它的生效范围、导入它，或者注册、移动一个智能体时，技能目标会在请求返回之前完成调和，所以变化立刻可见，而不是稍后才出现。
- **同步导入时**，以及切换某个[实验功能](/zh/guides/experimental-features)时，各自带着相应的授权。

各轮调和从不重叠。有些操作是连续的几次写入——切换提供商会先写投射再写智能体的记录；一轮同步会检出很多文件（每个文件都会发出提示），然后请求自己的导入调和——如果中间插进一轮调和，就会看到做了一半的状态，并把它「修复」回去。这样的操作在运行期间会*持有*调和器：其他所有轮次都要等待，而它自己请求的轮次在持有期间内运行。经由这类操作的修复不会等它自己，因为在一轮调和内部再次获取持有，不会多持有任何东西。

读取时失败的目标会被报告并跳过；其他目标照常调和。写入失败只会让它自己那一项失败，下一轮会再试。

## 只预览不写入 {#preview-without-writing}

同样的一轮可以以**试运行**方式执行：它计算出真正一轮会执行的完全相同的计划，但什么都不写——不写文件、不写数据库行、不写审计条目，连广播都没有。偏移视图和变更预览读的就是它：每一项的操作、文件、现有内容和将要写入的内容（渲染时确保不会出现任何密钥值），以及策略怎么说。因为是同一套计算，预览显示的就是一轮调和会做的事。

## 审计紧随写入 {#audit-follows-the-write}

每一次修复都会留下一条审计条目，而且这条条目在写入的同一步里记录，然后这一轮才继续——Coffer 自己跑的轮次用 Coffer 的自动身份，导入触发的轮次用同步身份，人自己应用的条目用这个人自己的身份。文件和审计日志存在不同的存储里，所以不存在跨越两者的事务，也不声称有。取而代之的是固定顺序：先写文件（保留备份），再记录条目。如果条目记录不了，文件就会恢复成备份里的内容——如果文件是这次写入新建的，就删掉它——这一项被报告为失败，下一轮会重试。恰好在两步之间崩溃，会留下一次未审计的写入，守护进程日志会记下它。

## 需要你处理的事 {#what-needs-you}

调和器自己修不了的偏移，是需要人来处理的几类事情之一。总览页的**待处理列表**把所有类型的这类事情汇总在一起：被报告或受阻的偏移，或者某一轮尝试修复但失败了的偏移；上次测试失败、启动器缺失或密钥缺失的 MCP 服务器；程序缺失或连接不完整的智能体；因冲突而停止、或者扣着删除等待确认的同步；正在重连、已断开或没有运行的消息渠道；有智能体在用、但接入地址无法连接或拒绝密钥的模型提供商。每种类型提供自己的信号；属于实验功能的信号只在该功能开启时出现。

每一项都说明它关于什么、原因（一个稳定的代码和一句话）、有多紧急、在已知的情况下首次发现的时间，以及恰好**一个操作**——与该类型自己的页面为它发出的请求相同。所以这个列表没有自己的写入。某个来源失败时，会在其他来源的条目旁边显示为失败，而不是把它们藏起来。还没有任何东西记录的信号——某个接入地址拒绝了提供商密钥、某个聊天平台拒绝了机器人令牌——不会去猜；它们将来会通过新增一个来源加入进来。

## 添加一个目标 {#adding-a-target}

给智能体新增一种资产类型，就是在投射注册表里加一个新条目，并在旁边加一个新目标。这个目标列出它的条目及全部参数，读取相同的形状，通过该类型带标记、原子、有备份的写入器写入，并声明它的策略——包括哪些触发（如果有的话）给它更强的授权。随它一起的测试对每个目标都一样：改变的参数能被发现并修复，策略不放行的差异被报告且保持不动，试运行什么都不写，审计失败的修复会被恢复。
