# 平台端口 {#platform-port}

Coffer 目前只发布 macOS 版本，但它的底层不允许假定自己跑在 macOS 上。本页讲清楚让这两点同时成立的思路：代码库里只有一个部分知道 Coffer 跑在哪个操作系统上，其他部分都去问它。只要你要写的东西在不同操作系统上行为会不一样，动手前先读这一页。这个决定本身以及当时权衡过的备选方案，记录在决策记录（ADR）[Platform Differences Live Behind One Platform Port](https://github.com/wyx-sg/Coffer/blob/main/docs/decisions/platform-differences-live-behind-one-platform-port.md) 里。

## 问题 {#the-problem}

一个管理文件、进程和桌面应用的本地工具，时时刻刻都在和操作系统打交道，而不同系统给出的答案各不相同。用用户的编辑器打开文件、在文件管理器里定位文件、弹出原生的文件夹选择器，在 macOS、Linux 和 Windows 上是不同的程序。技能在 macOS 和 Linux 上以符号链接的形式交付给智能体，但在 Windows 上创建符号链接可能需要特殊权限，所以那边的退路是目录联接（junction），再不行就复制。登录时启动守护进程，在 macOS 上是一个 launchd agent，在别的系统上没有直接对应物。就连「哪些目录属于系统、绝不能往里放技能」也取决于操作系统。

放任不管的话，每个差异都会在第一次用到的地方被就地回答，变成一个小小的「如果是 macOS」判断。Coffer 的应用层和基础设施层里都曾积攒了不少这类判断。代价有两个：

- **移植变成考古。** 支持第二个操作系统，就意味着要把散落各处的判断一个个找出来。漏掉的判断不会大声报错，而是在新系统上悄悄照着 macOS 的做法执行。
- **用例没法单独测试。** 按操作系统分支的服务，只能通过假装成每个系统来测，结果测试证明的是那个分支，而不是用例本身。

## 思路 {#the-idea}

只有一处知道操作系统，其他地方都去问它。

这一处放在基础设施层，因为回答操作系统问题属于适配器的活，和访问数据库、调用 SDK 是同一类工作。应用层不会直接伸手进去，而是把自己需要回答的问题声明成一个端口，由组合根把唯一一个了解宿主机的实现交给它。Coffer 里其他所有适配器都是这个形状（见[分层与代码布局](/zh/architecture/layering)）。基础设施层的其余代码与平台代码同处一层，可以直接使用它。

这些问题刻意做得很小，而且是「给答案」的形状：「这里用哪个命令打开这个文件？」「哪些路径是系统自己的？」，而不是「去把它做了」。判断路径是否有效、启动进程、把失败转换成用户看得懂的错误，这些仍由应用层决定。平台部分只提供每个操作系统上的事实。这样在测试里很容易用固定答案替换端口，一个用例只需测一次，与操作系统无关。平台部分则单独测试，每个操作系统测一次。

只有 macOS 的答案会随版本发布。如果另一个系统已经有已知且实现成本低的答案，比如 Windows 上的联接或复制、Linux 上常见的桌面工具，这些答案也放在同一处并有单元测试覆盖，但不宣称已支持。

## 哪些问题要经过它 {#what-goes-through-it}

目前平台部分回答这几类问题：

- **身份。** 当前是哪个操作系统、怎么向人描述它（比如写在某台机器的同步记录上），以及系统自己维护的稳定机器标识。
- **系统位置。** 哪些目录属于操作系统、其中哪些例外可以安全使用，以及路径比较上的怪癖，比如 macOS 会通过一个隐藏别名访问系统文件夹。
- **桌面操作。** 如何打开文件或文件夹、用指定编辑器打开、在文件管理器中定位、弹出原生文件夹选择器，以及判断某个编辑器是否已安装。
- **目录链接。** 如何用系统提供的最佳机制（符号链接、联接或复制）链接一个目录，以及如何识别磁盘上现有的是哪一种。
- **进程与服务。** 可执行文件叫什么、如何启动一个比父进程活得久的子进程，以及是否存在 launchd 这样的登录服务管理器。

还有几条操作系统假定尚未放到端口后面，因为它们从来没有显式的判断：在另一个程序打开文件时原子替换它、用信号停止进程、Coffer 为自己的二进制创建的链接、Coffer 写进某个智能体配置里的一段 shell 片段，以及 Coffer 自己主目录和各智能体默认配置目录的约定。这些在 macOS 上都不改变行为。把它们迁过来是该 ADR 的第二部分。

## 这条规则如何被守住 {#how-the-rule-is-protected}

导入规则做不到这一点。能暴露操作系统的标准库模块到处都有正当的导入，真正的信号是读取某个属性，而不是导入某个模块。所以 Coffer 有一个专门的构建门禁，作为 `make lint` 的一部分运行，也就是每次 `make verify` 和每个 pull request 都会跑。

这个门禁把源代码当语法树读，而不是当文本搜索。平台部分之外的任何代码只要读取操作系统名称、调用用来识别宿主机的标准函数，或者用别名导入这些名字，构建就会失败。因为读的是语法树，它能跟踪重命名的导入，也不会把一个恰好叫 "platform" 的普通变量误认成标准模块。它适用于所有层，包括基础设施层。测试不受限制，因为假装成别的操作系统正是测试覆盖各系统答案的方式。

门禁失败时，会指出它不认可的文件、行号和表达式。

## 出现新的依赖操作系统的需求时 {#when-a-new-os-dependent-need-appears}

新代码需要一个因操作系统而异的答案时：

1. **把知识放进平台部分。** 在那里添加各系统的答案，和同类答案放在一起。macOS 的答案要完全符合发布所需。Windows 和 Linux 能低成本给出真实答案就给，否则给一个调用方能处理的显式退路，比如「没有可用的选择器」或「用复制代替链接」。
2. **如果调用方在应用层，就通过端口来问。** 在端口上加一个问题，贴合用例需要知道的内容，并在宿主机实现里回答它。基础设施层的代码直接使用平台部分，跳过这一步。
3. **接收它，而不是去拿它。** 需要端口的服务在构造时接收它，由组合根传入它已经建好的那一个宿主机实现。
4. **两半分开测试。** 平台答案每个操作系统测一次，用例则配一个给固定答案的端口替身来测。

如果门禁标出了你原本没当作操作系统判断的代码，照样把它迁过去：一个取决于操作系统的值就是操作系统判断，不管它拿来做什么。
