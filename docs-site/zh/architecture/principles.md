# 原则 {#principles}

::: tip 本页具有约束力
本页是 Coffer 项目原则的唯一来源。它只收录**脚手架层面**的不变量：技术栈、工作流、许可证立场、架构风格，以及产品如何把工作交给智能体。产品行为——资源模型、谁可以驱动智能体的门槛、界面清单、什么数据存在哪里——按能力分别定义在 `openspec/specs/` 中。[四条原则](#the-four-principles)、[技术与架构约束](#technology-architectural-constraints)、[质量门禁](#quality-gates)和[治理](#governance)下的条款具有约束力；其余章节是对它们的解释。每个设计选择背后的理由见[设计理念](/zh/architecture/design-principles)。
:::

> Coffer 是一个本地优先的 AI 智能体保险库：开发者积累的 AI 资产
> 保存在自己的设备上，任何 AI 智能体（Claude Code、Codex 以及未来的智能体）
> 都通过同一个安全接口读取和贡献。

Coffer 是为解决一个具体的问题而生的。理解这个问题，是理解后面所有架构选择的最快途径。

## 问题 {#the-problem}

现代 AI 开发要用到许多 MCP 服务器——文件系统、数据库、浏览器、代码执行器、各类 API——以及多个 MCP 客户端：Claude Code、Codex，还有下个月发布的新工具。最朴素的做法是为每个客户端分别配置每个服务器：N 个客户端 × M 个服务器份配置，每一份都要手工维护，每一份都存着自己的一套 API 密钥 和密钥。服务器的 URL 一变、密钥一轮换，每个客户端的配置都得单独更新。更糟的是，同一个上游服务器暴露的工具名在不同客户端里可能不一样，因为每个客户端都有自己的过滤或别名规则。

结果就是密钥四处散落、客户端之间配置偏移，还有一个身份问题：Claude Code 里的 `read_file` 工具和 Codex 里的 `read_file` 可能是同一个，也可能不是。没有一个统一的控制点。

对这一块问题，Coffer 的答案是一个常驻的本地守护进程：上游 MCP 服务器只注册一次，所有服务器通过一个带命名空间的统一接口暴露出来（每个工具都显示为 `<server-name>__<tool-name>`），所有客户端连接都经过这一个点。配置一次，所有客户端看到的都是同样的工具、同样的名字、同样的策略。

不过，MCP 网关只是一个更大的保险库中的一项能力。同一个守护进程、同一套与类型无关的资源框架，还管理着已注册的编程智能体、技能主副本、共享知识库、汇总的智能体记忆、模型提供商和消息渠道——一共**七种**资源类型（`mcp_server`、`agent`、`skill`、`knowledge`、`memory`、`provider`、`channel`）——外加在消息渠道背后驱动这些智能体的横切轮次平台，以及与你自己的 git 远端之间的双向保险库同步。下面的原则约束的是整个保险库，网关是最早的那个类型，而不是系统的全部。

## 四条原则 {#the-four-principles}

其他一切——技术选型、分层、进程模型、持久化策略、产品如何向人求助——都是这四条原则的推论。

### I. 本地优先（不可协商） {#i-local-first-non-negotiable}

::: warning 不变量
所有用户数据都在用户自己的机器上——一个保险库，每台机器都持有完整状态。云服务只作为 LLM 和工具的提供方——它们永远不会成为任何保险库状态的记录系统。HTTP API 绑定在 `127.0.0.1`。要把用户状态复制到厂商控制的云上，必须修订原则。
:::

每一项保险库资产——已注册的服务器配置、密钥引用、审计日志、能力偏好——都留在你的设备上。没有用户的明确操作，不会有备份传到厂商云，也不会有遥测数据离开这台机器。

「本地优先」不等于「不联网」：调用远程 LLM API、调用云端托管的 MCP 工具都完全正常。这条约束管的是**状态存在哪里**，而不是是否使用网络。守护进程可以向 LLM 提供商发出 HTTP 请求；它只是不能在不修订原则的前提下，让第三方看到你的保险库状态。

**例外——用户自有的同步远端。** Coffer 可以让保险库与用户自己拥有的 git 远端收敛，使用户自己的多台机器共享一个保险库，而不是各持一份。这个例外受三个条件约束，**必须全部满足**：

1. 远端只是**汇合点，从来不是记录系统**——每台机器的本地保险库始终是权威且完整的，所以远端可以删掉，再从任意一台机器重建，不会丢任何东西。
2. 密钥**只以密文形式**传输，主密钥除了经由带外的密钥转移之外，永远不离开本机。
3. 该功能**默认关闭**，由用户针对自己拥有的仓库开启。

由 Coffer 自己运营的托管端点不在这个例外之内。

收敛是**双向的**：Coffer 既推送本机的改动，也应用远端带来的内容。它只在同步规格规定的安全规则下才被允许——由 git 自己的三方合并做裁决，应用的是**相对于本保险库可证明持有过的上一个状态的 diff**，而不是整体覆盖；一轮同步如果要删除的内容超过配置的比例，就会停下来询问。在这些规则之外写入保险库的机制，不受这个例外保护。一轮收敛如何满足这些规则，见[保险库同步](/zh/architecture/vault-sync)。

### II. 规格即真相（OpenSpec） {#ii-spec-as-truth-openspec}

`openspec/specs/` 下用 [OpenSpec](https://github.com/Fission-AI/OpenSpec) 编写的规格，是产品的正式契约。对外部可见行为的改动，先在 `openspec/changes/<id>/` 下作为一个 OpenSpec 变更出现，其中的规格增量写明改动之后什么会成立；然后与让它成立的代码一起落地，再归档进 `openspec/specs/`。规格不是「文档」——它是实现的契约；代码与规格不一致时，错的是代码。

之所以有这条原则，是因为分布式团队（以及生成代码的 AI 智能体）会随着时间推移偏离设计意图。把规格作为真相来源，并要求在改代码之前先更新它，Coffer 就能保证架构意图始终有记录、可验证。

**契约方向。** 一个规格目录的两半，是朝相反方向写的：

1. **行为规格**——`spec.md` 里的需求及其场景——先手工写好，代码照着它来实现。
2. **线上 schema**——同一目录下的 `contracts/api.openapi.yaml`——由后端的 Pydantic 模型生成并提交进仓库，所以它的每一处改动都会在引起它的那个 PR 里作为 diff 被审阅。
3. **前端的类型化客户端**及其线上类型，由这份 schema 生成。

两边都没有手写的线上类型。Pydantic 模型是 HTTP 线上格式唯一的手写描述，因为守护进程实际提供的就是它们。在它们旁边再手写一份 schema，就是第二份副本，只能靠门禁来保持一致，而按字段名比较两份文档的门禁，看不出类型、可空性或约束上的差异；从模型生成 schema 去掉了第二份副本，再从 schema 生成客户端，就能让 TypeScript 编译器检查每个使用方的类型，这是只比名字的门禁做不到的。理由记录在 [The wire contract is generated from the Pydantic models](https://github.com/wyx-sg/Coffer/blob/main/docs/decisions/wire-contract-generated-from-the-pydantic-models.md)。

### III. 从第一天起就为开源做好准备 {#iii-open-source-readiness-from-day-one}

许可证（MIT）、治理、贡献流程和 Conventional Commits 从 v0.0.1 起就在仓库里，而不是事后补上。任何会缩短这份清单的改动——未经例外批准就引入闭源依赖、对 AI 编写的内容省略署名——都违反这条原则，需要附带明确迁移计划的修订。

这避免了「以后再开源」的隐性成本——事后给代码库补许可证、署名和治理，代价高且容易出错。

### IV. AI 原生 {#iv-ai-native}

每个使用 Coffer 的人本来就在用编程智能体，所以 Coffer 把智能体当作完成依赖环境的工作的方式。当一个任务取决于这个人的机器、并且没有唯一正确的步骤时——安装程序、配置工具或外部账号、诊断和修复环境——产品就把它交给智能体。它会生成一段提示词，写明事实（缺什么、为什么需要、有哪些约束），并提供两种用法：复制下来给这个人自己的智能体，或者打开一个由 Coffer 托管的智能体的新对话，预先填好，只有在这个人按下「发送」后才发出。产品不会写死某个包管理器的安装命令，不会运行安装程序，也不会带着人走一长串手动步骤。那些人可以在界面里自己做、但未必想做的工作——解决同步冲突、把技能的上游更新与本地修改合并——也会在手动控件旁边提供交接选项，由这个人决定要不要自己处理。提示词由守护进程生成，所以命令行和界面给出的是同样的文字。

有两种情况不走交接：

1. **Coffer 自己负责、并且能确定且安全地完成的工作**——修复它在某个智能体配置里的条目、一轮调和、轮换它自己的令牌——就是一个普通按钮。
2. **只有这个人自己能做的工作**——在浏览器里登录、一次审批、在某个平台门户里的设置——留给这个人；提示词仍可以帮忙处理前后的步骤。

提示词从不要求智能体处理凭据；需要登录时，它会告诉智能体把登录留给人来做。

这样做成立，是因为写死的步骤只对一类机器是对的，对其余机器是错的，而且会随工具变化而过时，而智能体读的是它所在的那台机器。交接还让人保持掌控：在他们发送之前，什么都不会运行。

## 技术与架构约束 {#technology-architectural-constraints}

- **语言。** 后端、命令行和所有 MCP shim 使用 Python 3.12+；前端使用 TypeScript 5.x。没有修订就不引入其他主要语言。
- **架构。** 分层：`surfaces → application → domain`；`infrastructure` 适配 `application` 中定义的端口，只在组合根处接线。`domain/` 不得导入 `infrastructure/`、`surfaces/` 或外部 SDK。`application/` 不得导入 `surfaces/`。横切模块只在第二个功能需要时才抽取。（例外：资源框架——见[资源框架](/zh/architecture/resource-framework#design-decisions)——以及原则 IV 交给每个功能的、位于 domain 层的智能体交接——见[技能依赖](/zh/architecture/skill-requirements#the-agent-hand-off)。）各层、它们的强制机制和代码布局见[分层与代码布局](/zh/architecture/layering)。
- **持久化。** 保险库的文件是配置的记录系统：`~/.coffer/vault` 是一个 git 仓库，每一次被接受的写入都是一个经过校验、写明写入者的提交。历史（审计、调用、对话、同步轮次）存在 `runs.db` 中。大块用户内容——知识集、记忆分区——以文件形式存在本地文件系统上，这些文件就是唯一的副本：没有任何东西对它们做索引、切块或向量化。见[持久化](/zh/architecture/persistence)。
- **密钥。** 密钥**只**以 Fernet 密文存在，每个密钥一个文件（`vault/secret/<ref>.enc`，本机专属的引用则在 `local/secret/`）；明文只在解密到被消费它的进程启动或请求头注入之间存在于内存里。唯一长期持有明文的是本地模型代理，也是守护进程唯一的兄弟进程：它是一个请求头注入的消费者，在整个生命周期内把它所服务连接的已解密密钥留在内存中，通过带认证的回环控制路由从守护进程接收这些密钥，从不持有主密钥，也从不把密钥写到任何地方。Fernet 主密钥只由 `coffer.infrastructure.secret` 管理——在签名发布版中，是一个位于仅限 Coffer Team ID 的访问组里的数据保护 Keychain 条目；在开发构建中，默认是 `~/.coffer` 下一个 `0600` 权限的文件，选择开启时则通过 `keyring` 存进登录钥匙串。`keyring` 的导入只限于该模块。其他所有代码都使用密钥引用。密钥明文不会进入保险库、`runs.db`、日志、审计或任何结构化事件。密钥材料只以 Fernet 密文离开本机，而且只在用户明确要求时；主密钥永远不会写进保险库发布的任何内容，只通过显式的带外转移到达另一台机器（桌面应用在存在性校验之后写出的密钥备份，以及 `/sync/key/import`，它们只搬运密钥材料，不带别的）。见[安全](/zh/architecture/security)。
- **网络默认值。** 仅回环。Coffer 根据用户在表单里输入的内容、代表用户去探测或获取的 URL，发出的 HTTP 请求会先经过 SSRF 防护（`coffer.infrastructure.net.ssrf_guard`，它拒绝回环、私有和链路本地目标）。发往用户明确配置为自己端点的流量——HTTP MCP 上游、模型和语音转写接入地址、IM 平台、git 同步远端——在 Coffer 开始使用它们后不受此限，因为在这些场景里回环或局域网端点是正当目标（Ollama、本机的 MCP 服务器）。防护覆盖哪些调用，列在[安全 → 出站请求](/zh/architecture/security#outbound-requests)中。

## 质量门禁 {#quality-gates}

只有当以下**全部**成立时，一个改动才算「完成」：

- 相关规格已通过一个已归档的 OpenSpec 变更更新到与代码一致。
- 每条需求都有场景，每个场景都有通过的测试覆盖。
- `make verify` 在本地和 CI 中都通过。
- 文件大小限制成立（见 `.agents/stack.md`）。
- 没有违反架构边界。

## 治理 {#governance}

本页**取代** `AGENTS.md`、`CONTRIBUTING.md` 或各规格文档中任何相冲突的指引。它们不一致时，以本页为准。

**修订。** 修改任何一条核心原则、技术与架构约束或质量门禁，需要：

1. 一个提案 PR，描述动机、当前行为、提议的行为、下游影响和备选方案。
2. 在 PR 描述中记录明确的决定。
3. 修订 PR 同时更新本页（`docs-site/architecture/principles.md`）。它的历史就是这个文件的 git log。

**移除已发布的能力。** 移除一项已发布的能力，需要项目所有者明确确认。提出移除的 PR 必须在描述中说明回退的代价：它删除的代码、它对用户数据执行的迁移及其能否撤销，以及它改写的文档（规格、ADR、本页、OpenSpec 变更）。它必须在同一个 PR 里删掉死代码和所有文档引用，让代码树永远不会留下一个移除了一半、需要下一个读者去还原的能力。

**PR 审阅。** 每个 PR 的描述在适用时都必须写明它影响了哪些原则或约束，并解释这个改动为何遵守了（或正式修订了）它们。

## 保证与不变量 {#guarantees-and-invariants}

这些由上面的约束推出，无条件成立；它们不是配置项：

**仅回环。** 守护进程的 HTTP 服务器绑定在 `127.0.0.1`，不接受来自任何其他网络接口的连接。

**密钥明文永远不进存储。** 保险库的文件、`local/` 和 `runs.db` 存的是密钥引用——不透明的标识符——以及 `vault/secret/` 和 `local/secret/` 中的密文；从来不是明文。`infrastructure/secret/` 之外的代码都不得导入 `keyring`。

**每个上游工具都有命名空间。** 通过 Coffer MCP 接口暴露的工具显示为 `<server-name>__<tool-name>`（例如 `filesystem__read_file`）。这个命名空间稳定且确定：同一个上游以同一个名字注册，无论哪个客户端连接，得到的工具命名空间都一样。

**单一 SQLite 写入者。** 只有守护进程会写 `~/.coffer/runs.db`。命令行和 shim 通过守护进程的 HTTP API 读取状态，从不直接打开数据库。本地模型代理也不打开任何数据库：它把用量记录写成文件，由守护进程摄取。这个不变量让 WAL 模式的隔离天然正确。

## Coffer 不是什么 {#what-coffer-is-not}

理解范围和理解能力同样重要。

**不是云服务。** 没有托管的 Coffer，没有 SaaS 套餐，也不需要账号。守护进程就是你机器上的一个进程。

**不是托管的同步服务。** Coffer 只通过你自己拥有并配置的 git 远端让你的机器收敛；它不附带自己的远端，也没有托管的同步端点。要提供这样的东西，需要修订原则。

**不是模型提供商。** Coffer 本身不是 LLM，也不托管 LLM。MCP 网关只转发协议消息，不对工具输出做推理；消息渠道背后的轮次平台驱动的是你注册的编程智能体，它们确实会调用 LLM 来对话——但那些模型是 Coffer 调用的外部提供商，从来不是 Coffer 附带或训练的模型。Coffer 编排模型和工具；它本身不是模型。

**不是防火墙或安全边界。** Coffer 会在能力层面应用启用/禁用策略，但它是以用户自己的进程运行的开发者工具——它不对上游服务器代码做沙箱隔离，也不强制执行操作系统级的访问控制。

## 被否决的备选方案 {#rejected-alternatives}

这些否决记录在 ADR 中；这里的摘要用来锚定原则：

**为什么不用云端托管的网关？** 对团队来说，托管网关是很自然的方案，但它无条件违反本地优先。密钥必须离开本机；保险库状态会依赖网络。单用户、本地优先的模型是这个设计的根基。

**为什么不按客户端分别配置？** 按客户端配置就是现状——正是 Coffer 要解决的问题。它带来的痛苦（N × M 的维护负担、密钥散落、身份不一致）恰恰是需要一个中心守护进程的动机。

**为什么不提前抽取横切抽象？** 横切模块只在第二个功能需要时才抽取，以免过度设计。唯一的例外是资源框架，它是预先设计的，因为它横跨每一层（领域、持久化、审计、接口路由）——等到第二种资源类型出现后再补，就需要一次不小的迁移，而不是一次适度的抽取。
