# 技能依赖 {#skill-requirements}

驱动某个命令行工具的技能，在工具缺失时，会在调用它的那一步失败。技能依赖让这种失败在智能体撞上之前就有地方被看到：每个技能在 `SKILL.md` 里声明它的命令（这个人也可以手动添加工具），Coffer 在本机对每个命令检查一次，命令行工具页面、技能的**依赖**标签页和待处理列表会报告检查结果。面向用户的说明见[命令行工具指南](/zh/guides/clis)。

## 原则 {#principles}

- **技能的文件，或这个人在保险库里的声明，就是真相。** `requires:` 写在技能自己的 `SKILL.md` 里，每次检查都从主文件夹读取，所以它永远不会与用户编辑的内容偏移。这个人手动添加的工具，以及他对技能所需工具的显示名称和描述所做的修改，存在保险库文档 `state/cli-tools/tools.json` 里，会随同步走；修改会取代技能里的值。数据库里什么都不存。
- **只读声明。** Coffer 从不扫描技能的正文、脚本或子技能来猜它运行什么：从文字里猜，会列出技能只是提到的命令，又漏掉脚本真正调用的命令。把工作委派给另一个技能的技能，只声明它自己用到的东西；被委派的技能自己声明。要不要加声明、技能的结构怎么安排，都是这个人的智能体给出的建议，这个人可以拒绝（技能审阅交接）；技能必须满足的硬性规则只有[技能](/zh/architecture/skills)页上的导入限制。
- **在智能体运行的地方检查。** 查找用的是智能体真实的 `PATH`：登录 shell 的 `PATH`，与守护进程继承的 `PATH` 合并——和智能体探测用的是同一条查找路径，这也是它属于与类型无关的平台层、而不属于技能类型的原因。Coffer 启动的 Claude Code 和 Codex 会话，环境里拿到的也是这个 `PATH`，所以检查找得到的命令，智能体也找得到。
- **Coffer 只查命令在不在。** 命令是一个裸名字，在 `PATH` 上查找；Coffer 不运行它检查的任何命令，连 `--version` 也不运行。技能无法通过声明让 Coffer 运行任何东西。工具版本够不够新、登没登录，由智能体在使用它时自己发现（[ADR](https://github.com/wyx-sg/Coffer/blob/main/docs/decisions/agents-check-cli-logins-themselves.md)）；旧技能里带的 `min_version`、`version`、`login_check` 或 `login` 键，以及 `gh>=2.40` 这种写法，会被接受并忽略。
- **Coffer 负责检查；智能体负责安装。** 安装取决于机器——用哪个包管理器、什么架构、是否涉及 `sudo`——而这个人的智能体能弄清楚这些。Coffer 不运行任何安装程序，也不做登录。它把掌握的事实写进一段提示词，即[智能体交接](#the-agent-hand-off)，由这个人交给智能体。
- **每个命令一行。** 缺了 `gh` 就是一个问题，不管有多少技能需要它。
- **MCP 服务器的启动器也是依赖。** 已启用的 stdio MCP 服务器需要它的启动器，所以检查会把它列在提供它的命令之下（`uvx` 对应 `uv`，`npx` 对应 `node`，`bunx` 对应 `bun`）。这两种类型只在组合根处交汇：MCP 类型读取已启用服务器的启动器，组合根通过一个端口把它们交给检查，技能类型从不导入 MCP 类型。

## 组成部分 {#the-pieces}

| 部分 | 作用 |
| --- | --- |
| 声明 | 宽松地解析 `requires:`：用不了的条目带警告跳过，绝不会让技能导入失败。同一个 `requires` 还可以列出 Coffer 密钥（`requires: {secrets: [...]}`）；没设置的密钥会按名字报告，不读取任何值。 |
| 手动声明 | 这个人不经技能添加的工具，以及他对所需工具的修改，从 `state/cli-tools/tools.json` 读取。每次变更都审计为 `cli_tool_added`、`cli_tool_edited` 或 `cli_tool_removed`。移除一个技能也需要的手动添加工具，只会去掉这条声明。 |
| Coffer 自己的需要 | Coffer 自己运行的命令：`git`，用于保险库的历史和同步。 |
| 状态 | `missing` 或 `ready`，问题优先的排序，以及一个 stdio 启动器按哪个命令来检查。 |
| 汇总与缓存 | 在所有托管技能、已启用的 stdio MCP 服务器、手动添加的工具和 Coffer 自己的需要之间，每个命令一行：标题取这个人的声明或修改，其次是 Coffer 的需要，再次是第一个技能的；所有需要它的技能以及所有用它启动的服务器。结果会缓存，直到点「检查」或守护进程重启，读取时只探测还没检查过的命令；探测在工作线程中运行。 |
| 探测 | 在智能体的 `PATH` 上定位命令并解析符号链接；什么都不运行。 |
| 交接 | 针对缺失命令的提示词，作为 `handoff.prompt` 附在路由返回的每个命令上。 |
| 机器 | 提示词里写明的操作系统和 CPU 架构，例如 `macOS 15.6, arm64`，每个守护进程只读取一次。 |
| 待处理 | 类型为 `cli`，以命令作为 uid：`cli_missing`，提供 `check`。只有 MCP 服务器需要的命令不会产生待处理项：服务器自己的 `mcp_missing_launcher` 项已经点名了它。 |
| 接口 | `/api/v1/clis…`。 |

## 智能体交接 {#the-agent-hand-off}

Coffer 是 AI 原生的：依赖机器的杂事——安装、配置、排障——交给这个人的智能体，而不是由守护进程写成脚本。交接是任何功能都能用的一块积木：

- **一次交接由一个任务、若干事实和若干步骤组成**，由领域层中一个共享的渲染器把它变成提示词。功能提供它掌握的信息；渲染器写出一句任务说明、以 `-` 开头的事实行、每行一个的步骤，最后附上每次交接都有的规则——做任何需要 `sudo` 或修改系统设置的事之前先问这个人，把任何登录都留给这个人，不经手他们的凭据。
- **提示词在守护进程上生成**，通过功能自己的 REST 响应以 `handoff: {prompt}`（所有功能共用同一个 schema）提供，所以人复制出来的提示词就是页面提供的那一条。
- **Web 界面用一个共享组件显示它**：**交给 &lt;Agent&gt;**——它会在首选终端里启动默认的交接智能体，提示词作为它的第一条消息——以及它菜单里的**复制提示词**。提示词通过私有的临时文件传递，智能体在这个人的终端里、按它自己的权限模式运行。没有可用的托管智能体时——缺失的正是本该被询问的那个智能体，或者还没添加任何智能体——只提供「复制提示词」。
- **待处理列表也携带它。** 修复方式是一件杂事的待处理项带一个可选的 `handoff`，与其类型页面提供的提示词相同，原因说明里不点名任何命令。总览页的「需要你处理」行在该行的 ⋯ 菜单中提供它。

对于一个被依赖的命令，事实如下：

| 状态 | 提示词要求智能体 | 它写明的事实 |
| --- | --- | --- |
| `missing` | 安装它，为这台机器选择安装方式，确认能用后运行 `coffer cli check <command>` | 需要它的技能；用它启动的 MCP 服务器及其启动器；机器 |

`ready` 的命令不带提示词。当杂事是开放式的、依赖环境时用交接；当 Coffer 自己能确定地完成——再探测一次、连接一个智能体——就是一个普通按钮。

## 权衡 {#trade-offs}

- **页面上没有版本和登录状态。** 版本过旧或没登录的工具在智能体使用之前不会被标出来；智能体运行它时会看到工具自己的报错，而 Coffer 检查出的结果一分钟后也可能就过时了。Coffer 读版本对 `--version` 输出读不出来的工具（`go version`、`kubectl version --client`）本来也不管用。
- **提示词不写怎么确认。** 不是每个工具都有 `--version`，所以智能体用自己的方式确认，再运行 `coffer cli check`。
- **智能体在这个人的终端里安装。** 提示词要求它在做任何提权操作前先问这个人，而**交给 &lt;Agent&gt;**让智能体按它自己的权限模式运行，这个人可以看着它，并用 Esc 或 Ctrl-C 随时停下它。
