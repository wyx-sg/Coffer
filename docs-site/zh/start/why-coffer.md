# 为什么选 Coffer {#why-coffer}

本页解释塑造 Coffer 的几项决策，写给正在考虑是否采用它的读者。每一节都讲三件事：决策是什么、为什么这样定、实际用起来对你意味着什么。[设计原则](/zh/architecture/design-principles)页面讲的是同样的内容，但更深入。

## 本地优先 {#local-first}

**决策。** Coffer 的全部状态都在你的机器上，位于 `~/.coffer`。守护进程的 HTTP API 和 MCP 端点绑定 `127.0.0.1`，任何 `Host` 头不是回环地址的请求都会被拒绝。云服务永远只是提供方：你选择调用的模型和 MCP 服务器。它们都不是存放你保险库的地方。

**原因。** 智能体积累下来的东西属于你：工具、技能、笔记和 API 密钥。如果交给托管服务保管，你光是打开自己的配置就需要账号、网络连接，还得信任第三方。一个跑在回环地址上的进程，这些都不需要。

**对你意味着什么。**

- 不用注册。除了你用到的上游服务器或模型，Coffer 可以离线工作。
- 备份就是复制一个目录：先停掉守护进程，再运行 `cp -r ~/.coffer <backup>`。
- 网络上的任何东西都连不到守护进程。只有本机上能读取 `~/.coffer/daemon.json`（权限 `0600`）的进程才能拿到 API 令牌。

## 智能体自己的文件仍是事实来源 {#the-agent-s-own-files-stay-the-source-of-truth}

**决策。** Coffer 从不把智能体的配置、MCP 条目、插件、记忆或对话记录复制到自己的存储里。每次需要时，它都从智能体的文件中读取。Coffer 写入时，只写有文档说明、在允许列表内的条目：它自己的 `coffer` MCP 条目、你在界面里编辑的配置文件、插件开关。每次写入都是原子的，并留下 `.bak` 备份。编辑 Codex 的 TOML 时会保留你的注释和顺序。

**原因。** 智能体设置的第二份副本，在你改动原件的那一刻就过期了，然后就得有人来决定以哪份为准。直接读原件，就没有什么需要调和的。

**对你意味着什么。**

- 你可以继续手动编辑 `~/.claude/settings.json` 或 `~/.codex/config.toml`，Coffer 会立刻显示你的改动。
- 移除 Coffer 后，智能体照常工作。卸掉 Coffer 的 MCP 条目，智能体就回到它们自己的配置。
- Coffer 读取每个智能体的记忆，但从不写入。Coffer 生成的记忆笔记放在它自己的目录里。

## 一个 MCP 端点，而不是每个智能体一份配置 {#one-mcp-endpoint-instead-of-one-config-per-agent}

**决策。** 每个智能体的 MCP 配置里只有一条 `coffer` 条目，它运行 `coffer-mcp-shim`。Coffer 运行你注册的每个上游服务器，并以 `<server>__<tool>` 前缀列出它们的工具，所以两个服务器都有 `search` 工具也不会冲突。一个服务器暴露哪些工具、哪些智能体能看到它，都在 Coffer 里决定，而不是在每个智能体里分别设置。

**原因。** 有 N 个智能体和 M 个服务器时，否则你得手动维护 N×M 条配置。一个端点把它变成 M 次注册。这也让 Coffer 有了一个统一的位置，可以按智能体施加范围控制，并记录每次调用（哪个工具、什么时候、耗时多久、结果如何，但从不记录参数或返回内容）。

**对你意味着什么。**

- 用 `coffer mcp add` 注册一次服务器。每个装了 Coffer 的智能体在下一次会话中就能拿到它的工具。
- 目录超过预算（默认 50 个上游工具）后，`tools/list` 只显示最常用的工具。内置的 `coffer__search_tools` 工具可以搜索完整目录，而且每个工具仍然都能调用。
- 每个智能体会话都有自己的上游子进程，所以两个智能体同时工作不会互相干扰。

会话、命名空间和工具分层如何工作，见 [MCP 网关](/zh/architecture/mcp-gateway)。

## 知识靠拉取，而不是推送 {#knowledge-is-pulled-not-pushed}

**决策。** Coffer 不会把知识塞进智能体的提示词。一个知识集就是 `~/.coffer/vault/knowledge/` 下的一个 Markdown 文件夹。Coffer 投递一个它自己的技能 `coffer-guide`，里面列出每个知识集的所有文档，带路径、标题和描述。智能体用自己的 `Read` 和 `Grep` 工具读取需要的内容。Coffer 不对这些文件做索引、分块或向量化。

**原因。** 依赖智能体记得去调用某个特殊工具的检索方式，往往会被跳过。每个受支持的智能体本来就能读文件。智能体需要的是知道有哪些文件、在哪里，一份目录就够了。让文件成为唯一副本还意味着：你在自己的编辑器里改了文档，下一次读取就能拿到改动。

**对你意味着什么。**

- 你的知识是普通 Markdown，可以用任何工具打开、grep、做版本管理和编辑。
- 智能体通过 `coffer__write` 添加材料。一轮整理（如果你配置了 Coffer 自己的模型，就由它来跑）会把新材料合并进已有文档。
- 记忆正好反过来。Coffer 提炼出的记忆是推送的，通过一个你为每个智能体显式安装的 Hook：会话开始时推送索引，提示词提到的笔记推送给它，你绑定到某条命令的笔记在该命令运行前推送。[记忆指南](/zh/guides/memory)解释了具体做法。

## 密钥用你持有的主密钥加密 {#secrets-are-encrypted-with-a-key-you-hold}

**决策。** 密钥只以 Fernet 密文形式保存，每个密钥一个文件，位于 `~/.coffer/vault/secret/`。配置里从不存放密钥本身，而是存一个*密钥引用*（secret ref），即一个名字，比如 `github.token`。守护进程只在启动上游服务器或发送请求头的那一刻才解密密钥。默认情况下，主密钥是一个权限为 `0600` 的文件 `~/.coffer/master.key`，它永远不会进入保险库。你也可以把它移到 macOS 钥匙串里。

**原因。** MCP 服务器配置和提供商配置都需要 API 密钥。如果以明文保存，每一次导出、每一行日志、每一个同步提交都会让它们面临风险。有了引用，系统的其余部分永远接触不到明文。

**对你意味着什么。**

- 用 `coffer secret set <ref>` 保存密钥，它会提示你输入值（不回显），也可以从 stdin 读取；在其他地方都按名字引用它。
- 明文永远不会进入保险库、日志或审计日志。
- 丢了主密钥，就丢了所有已保存的密钥。像对待 SSH 私钥一样对待 `~/.coffer/master.key`。

完整的威胁模型见[安全模型](/zh/architecture/security)。

## 同步走你自己的 git 远端 {#sync-goes-through-a-git-remote-you-own}

**决策。** 要在几台机器之间共享一个保险库，就让每台机器都指向一个你自己的 git 仓库。在你配置之前，同步是关闭的。保险库本身已经是 git 仓库，所以后台 worker 只需 fetch、让 git 合并、再 push。干净的合并直接应用；只要有冲突，这一轮就停下，两边都不做任何改动，直到你逐个文件做出选择。如果一轮同步会删除超过设定比例的保险库内容，它会先停下来问你；每一轮都可以回滚。密钥只以密文形式传输。主密钥只有在你亲自运行带外传输命令（`coffer sync key`）时才会在机器之间转移。

**原因。** 由 Coffer 运营的服务会打破本地优先的原则。你掌控的 git 远端只是一个汇合点，而不是记录系统：每台机器都保有完整的保险库，所以你可以删掉远端，再从任意一台机器重建。

**对你意味着什么。**

- 托管方由你选（GitHub、GitLab、你自己的服务器），Coffer 做的每个提交你都能读到。
- 有些设置只留在各自的机器上。资源的*生效范围*（在本机是否启用、哪些智能体可以使用）不同步，每台机器自己决定。
- 新机器用 `coffer sync join` 加入。它会展示加入后会发生什么，不删除任何东西，并在应用前征求你的同意。

每一轮同步的细节见[保险库同步](/zh/architecture/vault-sync)。
