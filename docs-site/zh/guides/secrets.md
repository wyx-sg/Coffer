# 密钥 {#secrets}

Coffer 替你的智能体保管密钥，而你的智能体以你的身份运行。本页解释 Coffer 在两者之间划的那条线，以及日常如何与它配合：存入不属于任何资源的密钥、带着它运行命令、处理 Coffer 发来的审批、查找谁在用某个密钥，以及备份主密钥。

资源自己的密钥——MCP 服务器的令牌、提供商的 Key——如何存入、引用、轮换和删除，见[密钥存储](/zh/guides/secret-store)。这一切背后的威胁模型见[安全模型](/zh/architecture/security)。

## 用大白话说 {#the-idea-in-plain-words}

编程智能体可能读到一个恶意的网页、issue 或 README，然后开始照着里面的指令做。这样的智能体用的是你的 shell：它能读你的文件、运行 `coffer`、调用 Coffer 的 API，和你完全一样。Coffer 不去阻止它配置 Coffer——替你把 Coffer 配好本来就是智能体的活。Coffer 保护的是**密钥**本身：

1. **只有你，在桌面应用前，才能看到密钥的值。** 没有任何命令、REST 路由或 MCP 工具会返回已存储的值或主密钥。显示或复制一个值、备份主密钥，都只能在桌面应用里进行，而且每次都要单独通过 Touch ID 或登录密码验证。智能体可以用 `coffer secret reveal` 或 `coffer secret backup-key` 发起，但值只显示在应用窗口里，从不出现在命令的输出中。下一次显示会再问一遍。
2. **密钥要去新的地方，必须先经你批准。** 把一个已有的密钥发往它从未去过的地方——新的 MCP 服务器、改过的命令行、另一个 git 远端——要等你在桌面应用里批准。智能体可以用 `coffer approval approve` 请求这次批准，但在场验证仍在应用里、在你面前进行。批准之前，什么都不会发出去。
3. **关掉这些保护，同样需要你在桌面应用前操作。** 没有任何环境变量、配置文件或参数能做到。
4. **智能体拿到的是能力，不是钥匙。** 网关把 HTTP 服务器的令牌直接放进请求里，所以智能体看到的是工具的结果，从来看不到令牌。

写入资源的密钥对所有入口都开放：能提供值的人本来就拥有它。存入密钥会立即生效，无论是新的独立密钥，还是给正在使用的密钥换新值。

## 密钥页面 {#the-secrets-page}

侧边栏系统分组中的 **密钥**（`/secrets`）是 Web 界面里唯一一个列出并管理已存储密钥的地方。密钥只来自 Coffer：资源自己对话框里的密钥字段——MCP 服务器的令牌、提供商的 Key——要么从这个页面选一个已存的密钥，要么接受一个粘贴的值并随表单存到这里；请求头或环境变量的行则是明文，字段末尾有一个 🔑 按钮，可以改为选一个已存的密钥。粘贴进明文行、看起来像密钥的值会提示你存起来。资源自己的设置里不放任何机密，只有密钥的 id。这个页面让你把它们放在一起看，并知道每个是做什么用的。

页面是左右分栏：左边是列表，右边是你选中的密钥，地址为 `/secrets/<id>`。

每个密钥都有一个固定的 **id**——它的引用，配置和文件里引用的就是它——以及一个随时可以修改的**名称**，外加可选的**描述**。修改名称或描述不会影响任何引用该密钥的地方。

**列表。** **查找密钥**（或按 `/`）按名称、描述或 id 筛选，**状态**筛选标签把它缩小为**全部**、**使用中**（有东西引用它）或**未被使用**（没有任何东西引用，可以安全删除）；密钥按**使用中**和**未被使用**两个标题分组。每一行只显示名称（描述在密钥详情的页眉里），以及状态（**这台 Mac 上没有值**、**等待批准**，以及一个终端图标，表示以你身份运行的其他程序能读到这个值）和有多少处在用它（“2 处使用”）。没起名字的密钥显示用它的东西和它占用的槽位，例如 **confluence · CONFLUENCE_PERSONAL_TOKEN**。页眉有 **添加密钥** 和 **查找明文密钥**。

要一次删除多个，勾选若干行（或用表头复选框选中整个列表）；列表上方的操作栏显示“已选 3/8”并提供 **删除…**，按 **Esc** 清除选择。确认框会列出将要删除的密钥，并说明所选中因为正在使用或等待批准而被跳过的那些。

### 这台 Mac 上缺失 {#missing-on-this-mac}

当这台 Mac 没有值可以交出去时，该行显示 **这台 Mac 上没有值**：某个资源或技能引用了它，但它从未在这里存过；或者它的加密值是随保险库从另一台 Mac 同步来的，而这台 Mac 没有那台的主密钥（加密密钥默认不同步）。用到它的东西在拿到值之前都无法启动。详情里的 **添加值**（或 **添加值** 对话框里的一个输入框）可以存入一个值；和任何写入一样，它可能需要[等你批准](#approvals)。只要有密钥缺失，页面顶部就会出现横幅，统计缺失的数量（“3 个密钥在这台 Mac 上没有值”）、列出它们，并提供 **添加值**：一个对话框，每个缺失的密钥一个输入框，留空的仍然缺失，**保存 N 个值** 存入其余的。同样的数量也出现在[总览](/zh/guides/web-ui#overview)上，那里的按钮会打开这个页面。一下子打开所有密钥的另一种办法是另一台 Mac 的主密钥，它在[保险库同步](/zh/guides/vault-sync)的加入流程或设置 › 安全里导入，而不在这个页面。Coffer 判断一个密钥是否打不开，靠的是用这台 Mac 的主密钥校验加密值的签名，不解密任何东西。

选中一行，该密钥就在右侧打开。它的页眉显示**名称**，下面是**描述**（没有描述就不显示），旁边是 **编辑** 和 **显示值…**，以及一个 **⋯** 菜单。页眉下面直接显示密钥的 id 和它的 `coffer://secret/<id>` URI，各带一个 **复制** 按钮（**复制引用**、**复制 URI**）；这台 Mac 是否持有该值、其他本机进程能否读到它；对独立密钥，还有一行**访问**，说明 `coffer run` 能否使用它（见[允许 `coffer run` 使用它](#allow-coffer-run-to-use-it)）；创建时间和上次使用时间；以及**使用方**——用到它的每一项，按类型（MCP 服务器、模型提供商、消息渠道、技能……）、当前名称和槽位列出，并附上它已获得或正在等待的审批。点名称即可打开对应的页面。反过来，别处的页面显示某项在用的密钥时（模型提供商的 **API Key**、同步远端的推送密钥），显示的是密钥的名称，点名称就打开这里对应的密钥；id 和 URI 只出现在这里，供复制。具体的每次使用不在这里列出，到[活动](/zh/guides/activity)里看。

| 控件 | 作用 |
| --- | --- |
| **编辑** | 打开一个对话框，修改**名称**（最多 64 个字符）、**描述**（最多 200 个）和**值**。名称和描述随保险库同步，不影响任何引用该密钥的地方。值的输入框一开始是空的，从不显示旧值：留空就保留当前值，填入新值则立即替换。对话框会列出使用该密钥的东西。对于[这台 Mac 上没有值](#missing-on-this-mac)的密钥，填入的值会被存入。 |
| **显示值…** | 只在桌面应用中可用——见[查看或复制一个值](#see-or-copy-a-value)。浏览器中它显示为禁用的 **在 Coffer 应用中显示**。 |
| **⋯ › 复制引用（…）** | 复制文件或配置里要引用的内容，菜单项里会显示出来：独立密钥是 `coffer://secret/<id>`，其他密钥是 ref。 |
| **⋯ › 删除…** | 对没有任何东西在用的密钥，询问一次，然后删除——在这台 Mac 上删除；如果加密密钥开启了同步，你的其他 Mac 也会在下一轮同步时删除。对仍在使用的密钥，它什么都不删：对话框列出仍在用它的每一项，附带 **打开** 跳过去，该密钥保留。 |

**查找明文密钥** 在 Coffer 管理的东西里找以明文写着的凭据：你的技能文件，以及每个已登记 MCP 服务器的环境变量和 HTTP 请求头（自定义工具的请求头也在内）。它能识别 200 多种凭据格式（云服务密钥、代码托管和聊天工具的令牌、支付密钥、私钥等，来自开源的 [gitleaks](https://github.com/gitleaks/gitleaks) 规则集）、赋给名字里带 password 的键的密码，以及写在 URL 里的密码。每一项都会显示发现它的规则，例如 `stripe-access-token` 或 `generic-api-key`。引用、`$VAR` 或 `${VAR}`、双花括号模板、`<your-token>` 这类占位符，以及只说明值从哪里来的代码，都不会被当成明文。同一套检测也在守着[保险库同步](/zh/guides/vault-sync#when-a-round-finds-a-plaintext-secret)。对话框按技能和 MCP 服务器分组列出找到的项——技能的文件和行号，或服务器的 `env`/`header` 键名，以及各自会变成什么——从不显示值，默认全部勾选。取消勾选要保留的，然后点 **查看 N 项改动**：Coffer 先算出要做的移动但不写任何东西，列出将新增的密钥和将修改的文件与服务器。**应用 N 项改动** 执行移动：

- 技能里的值变成一个以发现项命名的独立密钥，文件里原来的位置改为引用 `coffer://secret/<id>`（脚本里怎么用见[带着密钥运行命令](#run-a-command-with-a-secret)）。Coffer 改写不了的文件保留原值：值照样存入，对话框会指出这个文件并提供 **重试**。
- 服务器里的值变成这个服务器自己的密钥，在服务器配置里以同一个变量名或请求头名引用；服务器拿到的值和以前一样，不需要批准。像 `Authorization: Bearer abc…` 这样的请求头会被拆开：`abc…` 成为密钥，这一行的方案设为 Bearer。

每次移动都会以“导入了密钥”记录在[活动](/zh/guides/activity)里，不含值。什么都没找到时，会说明读了多少个文件和服务器。

**不是密钥。** 如果某一项只是示例或测试值，在它上面选**不是密钥**。Coffer 会在这台 Mac 上记住这个值，此后不再报告它——这里不报，保险库同步推送前的检查也不报——无论它在哪里、所在文件怎么改；值本身改了才会再报。Coffer 只保存用你的主密钥算出的值指纹，从不保存值本身。**显示已忽略（N）**列出你标记过的项，可以用**重新报告**撤销。两种操作都会记入[活动](/zh/guides/activity)，不含值。

**规则从哪里来。** 规则取自 gitleaks 的某一个固定发布版本，随应用一起内置，采用 MIT 许可；Coffer 在其上加了自己的白名单和针对密码的规则。规则在每次 Coffer 发版时由人工刷新，所以新的凭据格式要随更新才会到你手上。经过编码（base64 或十六进制）的内容不会被解码后再扫描。

**添加密钥** 用来新增一个独立密钥：一个名称、可选的描述和一个值，值不会再显示出来。Coffer 会生成它的 id，即 `secret/<id>`，然后对话框显示 `coffer://secret/<id>` 和 **复制** 按钮——脚本或技能引用的就是它。密钥在你添加后立即存入，无需批准——但在你[允许](#allow-coffer-run-to-use-it)之前，`coffer run` 用不了它。在这里添加的密钥，或用 `coffer secret set --name` 添加的密钥，在第一次被某个资源引用时需要你批准；见[审批](#approvals)。

要在命令里用已存储的密钥，见[带着密钥运行命令](#run-a-command-with-a-secret)。

只要有改动在等待批准，页面顶部就有一条横幅显示数量（“1 项改动等待批准”），并说明在这里批准需要什么——桌面应用里是 Touch ID 或登录密码；浏览器里则需要去桌面应用——另附 **查看** 重新打开审批对话框。总览上有同样的一项，它的 **查看** 打开同一个对话框。横幅的 **×** 会忽略它，页面和总览一起生效：页面随后显示“… — ignored on Overview. Show it again”，情况变化时这一项会自己回来。一个密钥都没有时，页面提供 **添加密钥** 和 **查找明文密钥**。

## 独立密钥 {#standalone-secrets}

大多数密钥属于某个资源，由注册该资源的对话框存入。**独立密钥**不属于任何资源：比如某个技能脚本需要的数据库密码，或你在终端里用的内部 API 令牌。它和其他密钥放在同一个加密存储里，位于 `secret/<id>` 下，文件中以 `coffer://secret/<id>` 引用它。

id 总是由 Coffer 生成，在密钥页面和 `coffer secret set --name "<name>"` 里都一样；你从不自己选 id。你只需要选一个**名称**和可选的**描述**，而且随时都能修改，因为它们是保存在保险库里、紧挨着密钥并随之同步的备注。id 永不改变，所以在密钥页面上给密钥改名，不会影响任何引用它的地方。当对话框要你选一个密钥时，它的选择器按名称列出密钥，并把 id 写进配置。

每一种密钥都是这同一种形状。你粘贴进某个资源自己对话框的密钥——MCP 服务器的令牌、提供商的 Key——同样生成为 `secret/<id>`，并归该资源所有（见[密钥存储 → 删除密钥](/zh/guides/secret-store#delete-a-secret)）。

### 存入一个 {#store-one}

```sh
# From stdin, so the value never reaches your shell history
printf '%s' "$ORDERS_DB_PASSWORD" | coffer secret set --name "Orders DB"
# stored: Orders DB
#   id:  secret/<id>
#   uri: coffer://secret/<id>

# Or at a hidden prompt
coffer secret set --name "Orders DB"
```

命令会打印新的 id 和它的 `coffer://secret/<id>` URI；要引用的就是它。`coffer secret set <已有的 ref>` 只会替换一个已存在的密钥的值，从不新建密钥，而且不是 `secret/<id>` 的 ref 会被拒绝。

在[密钥页面](#the-secrets-page)上，**添加密钥** 效果相同：一个名称、可选的描述和一个值，然后是供复制的 URI。新密钥会立即存入。只有你在该密钥的页面上[允许它](#allow-coffer-run-to-use-it)之后，`coffer run` 才会解析它。

### 引用它 {#cite-it}

在技能或项目需要这个密钥的地方，写它的引用而不是值：

```sh
# connection.env, next to a skill's script
DB_HOST=db.internal
DB_USER=orders_ro
DB_PASSWORD=coffer://secret/<id>
```

技能的 `connection.md` 也用同样的方式写。只含引用的文件可以放心提交，也可以放心同步。它本身不会被任何东西读取：[`coffer run`](#run-a-command-with-a-secret) 在命令启动时解析其中的引用，对象是你已[允许它使用](#allow-coffer-run-to-use-it)的每个密钥（引用了某个密钥的技能，需要对该密钥允许一次）。

资源也可以引用独立密钥，在它的 secret refs 里写 `secret/<id>`，和其他 ref 一样。

## 带着密钥运行命令 {#run-a-command-with-a-secret}

`coffer run` 在你允许之后（见下一节）通过守护进程解析独立密钥，然后启动一个命令，并且**只在这个命令的环境里**设置这些值。密钥的 id 不是变量名，所以变量名要你自己指定：

```sh
coffer run --secret PGPASSWORD=coffer://secret/<id> -- psql -h db.internal orders
coffer run --env-file connection.env -- ./query.sh
```

| 选项 | 含义 |
| --- | --- |
| `--secret ENV=coffer://secret/<id>` | 把 `secret/<id>` 设为变量 `ENV`。可重复。应该用这种形式，技能里引用密钥也用这种形式：这样该密钥的**使用方**会列出这个技能。`ENV=<id>` 同样可用。 |
| `--secret coffer://secret/<id>` 或 `--secret <id>` | 把 `secret/<id>` 设为一个变量，变量名由 id 推导而来（转成大写，`-` 和 `.` 换成 `_`）。由于 id 是一串十六进制字符，推导出的名字很少是命令想要的；建议用 `ENV=coffer://secret/<id>`。 |
| `--env-file FILE` | 读取 `KEY=VALUE` 行。普通值原样传递；每个 `coffer://secret/<id>` 值都会被解析。 |
| `--no-masking` | 原样透传命令的输出，用于需要真实终端的工具。 |

`coffer run` 自己环境里已有的 `coffer://secret/<id>` 值也会被解析，所以包装脚本可以一次性导出这些引用。`--` 之后的所有内容都是命令及其参数。

具体行为：

- **只解析你允许过的独立密钥。** id 必须存在 `secret/` 下；资源的密钥永远不能通过这种方式取出。未知 id 会以 `SECRET_NOT_FOUND` 失败，尚未允许的密钥按[下面](#allow-coffer-run-to-use-it)所述失败，两种情况下命令都不会启动。
- **值只给子进程。** 运行 `coffer run` 的 shell 拿不到它们，这个 shell 的其他子进程也拿不到。
- **输出会被遮蔽。** 命令的标准输出和标准错误中，每一处与值完全相同的内容都显示为 `***`，即使它被拆在两次写入里。短于 8 个字符的值不遮蔽——遮蔽短值会把正常输出搅得支离破碎——跳过时 `coffer run` 会告诉你。
- **退出状态原样传回**，所以 `coffer run` 可以放进脚本里用。被信号杀死的命令以 `128 + signal` 退出；无法启动的命令以 `127` 退出。`Ctrl-C` 和 `SIGTERM` 会转发给命令。
- **每次解析都记入审计**，事件为 `secret_resolved`，记录密钥名称、程序和工作目录——从不记录值，也不记录命令行的其余部分，因为那里可能带着别的密钥。用 `coffer log audit --event-type secret_resolved` 查看。

::: warning `coffer run` 防的是失误；防智能体靠的是“允许”这一步
`coffer run` 能让密钥**不至于因为失误**进入文件、git、智能体自己的环境和对话记录。谁运行这个命令，谁就拥有子进程，也就能读它的环境（`ps eww`）、运行 `coffer run --secret TOKEN=<id> -- env`，或者把值用 base64 编码后打印出来，而遮蔽认不出编码后的值。所以智能体的 `coffer run` 只对**你**允许过的密钥有效。只需要让智能体*使用*的密钥，应当保持不允许，让它通过 Coffer 到达服务：MCP 服务器（由守护进程把密钥放进服务器的环境或 HTTP 头），或自定义 HTTP 工具（由守护进程发出请求）。这层保护的局限见[安全模型 → 仍然暴露的部分](/zh/architecture/security#what-stays-exposed)。
:::

### 允许 `coffer run` 使用它 {#allow-coffer-run-to-use-it}

只有你允许本机程序使用某个独立密钥，`coffer run` 才会拿到它。这个允许和本页的其他审批一样，每个密钥一次，在桌面应用里用 Touch ID 或登录密码回答。它从不通过默认值、关闭审批保护，或者“刚提供过这个值”而自动给出。

在密钥页面上，独立密钥的详情里有一行**访问**：

| 访问 | 你看到的 | 含义 |
| --- | --- | --- |
| **关闭** | **允许 `coffer run`…** | `coffer run` 不能使用这个密钥。在桌面应用里，按钮会立刻请求 Touch ID 或登录密码，验证后直接开启；取消验证的话，请求保持等待。在浏览器里，它只记录请求，等桌面应用批准。 |
| **等待中** | 等待在 Coffer 应用中批准 | 在那里批准，或者**拒绝**。 |
| **开启** | **撤销** | `coffer run` 可以使用这个密钥。**撤销**立即生效，不需要存在性校验，因为它只会收窄访问。它记录为 `secret_local_access_revoked`。 |

没有允许时，`coffer run` 什么也不启动、不打印任何值，并以非零状态退出。请求会留在桌面应用的审批里等待（`SECRET_BINDING_PENDING`）；如果你拒绝了，命令会回答 `SECRET_BINDING_REJECTED`，直到你在该密钥的页面上再次点 **允许 coffer run…**，重新提出一条请求。智能体看到其中任何一个，都应该告诉你它需要哪个密钥，而不是重试。

如果你已有引用了 `coffer://secret/<id>` 的技能，请在每个这样的密钥的页面上各允许一次；技能本身不用改。

## 查看或复制一个值 {#see-or-copy-a-value}

在**桌面应用**中打开[密钥页面](#the-secrets-page)，在该密钥的详情里选择 **显示值…**。先会弹出警告：任何能看到你屏幕的人都能读到这个值。然后 macOS 要求 Touch ID 或登录密码，提示中会写明是哪个密钥。值显示 30 秒，附带 **复制** 和 **隐藏**，然后再次隐藏；关闭对话框会立即丢弃它。每次显示都会重新询问；不存在一个“第二次免验证”的时间窗口。显示以 `secret_revealed` 记入审计，只记录 ref。

浏览器界面不提供显示：该按钮显示为 **在 Coffer 应用中显示** 且处于禁用状态。

在终端里，`coffer secret reveal <ref>` 请桌面应用执行同样的显示流程，应用没在运行时会先启动它。提示和值都出现在应用里；命令只知道你是否完成了验证（退出码 `0`）或没有完成（退出码 `11`），从不打印值。

## 审批 {#approvals}

在密钥页面上或用 `coffer secret set --name` 添加的密钥不属于任何资源，所以第一次有资源引用它时，也要等人来批准。审批是一个会扩大密钥去向的改动，它会被扣住，直到你在桌面应用里回应。

### 哪些操作需要审批 {#what-asks-for-approval}

| 你或智能体做了这件事 | 等待的是什么 |
| --- | --- |
| 注册一个资源，它引用了一个已经发往别处的密钥，比如第二个使用同一令牌的 MCP 服务器。 | 在你批准前，新服务器拿不到密钥。第一个照常工作。 |
| 改变某个资源发送密钥的去处：stdio 服务器的命令、参数、工作目录或其他环境变量；HTTP 服务器的 URL；SeaTalk 消息渠道的应用。 | 在你批准新目标前，该资源拿不到密钥。 |
| 让某个资源改用另一个已存的密钥（**更换密钥… › 改用其他密钥**）。 | 在你批准这个密钥给它用之前，该资源拿不到能用的密钥。 |
| 把同步远端的推送令牌指向另一个 URL。 | 在你批准前，远端不会被保存。 |
| 请求让某个独立密钥可被 `coffer run` 使用（**允许 `coffer run`…**，或智能体带着它运行 `coffer run`）。 | 在你批准前，`coffer run` 什么也不启动。见[允许 `coffer run` 使用它](#allow-coffer-run-to-use-it)。 |
| 在**设置 › 安全**里关闭密钥审批。 | 在你批准前，保护保持开启。 |

关键在于**目标**——真正接收这个值的东西，写成你能据以判断的样子：stdio 服务器的完整命令行，连同它的工作目录和其他环境变量（像 `NODE_OPTIONS=--require …` 这样的变量会改变进程的行为）、HTTP 服务器的 URL、git 远端的 URL、消息渠道的机器人或应用。一条审批读起来像这样：

```text
send secret 'github/token' to mcp_server 'gh-work' (GITHUB_TOKEN) at stdio npx -y @modelcontextprotocol/server-github
```

只批准你认得的目标。一条不是你写的、指向临时目录里某个脚本的命令行，正是被注入的智能体会注册的东西。

### 你在桌面应用里做的改动 {#approve-on-save}

Coffer 分不清是你点的还是智能体调用了同一个 API，所以你自己做的改动也要过存在性校验——但在桌面应用里，它就是保存的一部分。当**保存**（或**改用此密钥**、**添加**、**创建分组**……）让你刚保存的东西留下一条待批准时，应用会立刻请求 Touch ID 或登录密码，提示里写着这条审批自己的描述，批准的正是这一处改动，不用再去打开审批面板。取消提示的话，这处改动保持待批准，显示在它自己的页面上，你可以在那里或审批面板里再批准。浏览器里没有存在性校验，改动会等桌面应用来批准。

### 哪些操作不需要审批 {#what-needs-no-approval}

- **为该资源创建的密钥。** 你粘贴进某个资源自己对话框的密钥——MCP 服务器的令牌、提供商的 Key——是为该资源生成的并归它所有，所以注册这个资源时不需要为它另外批准。第二个引用同一密钥的地方就是第二个地方，需要等待。
- **保护关闭期间的任何操作**——但 `coffer run` 的允许除外，它总要等你。

绑定关系在你注册或修改使用它的地方时也会检查，所以它需要的审批会在你保存时立刻出现，审批对话框会在你所在的页面打开。绑定关系在使用时同样会检查——服务器启动时、消息渠道连接时、一轮同步推送时——所以绕开 Coffer 发生的改动，比如手工编辑的保险库文件，或另一台机器同步过来的服务器，也会被拦住。

### 如何处理一条审批 {#answering-one}

有东西在等待时，桌面应用会发一条通知 **Coffer needs your approval**，写明是什么改动，并打开审批对话框，一张表，每条改动一行：改动的类型（**新的使用处**、**关闭保护**）、涉及的密钥、发往哪里（谁在使用它，或接收它的目标）、谁发起（**You · in the Coffer UI**、**You · on the command line**、**Through the API**）以及何时。只有一条改动时，**批准…** 会发起 Touch ID 或登录密码验证，提示中写明是什么改动，然后应用改动；服务器、消息渠道或远端会在下一次尝试时取到密钥，无需重启。**拒绝** 不需要在场验证，因为拒绝只会收窄 Coffer 的行为。

在浏览器中，**批准** 是禁用的——“请在 Coffer 桌面应用中批准”——只有 **拒绝** 可用。智能体可以用 `coffer approval approve <id>` 把提示带到应用里（见[在命令行上](#on-the-command-line)）。

### 一次处理多条 {#answering-several-at-once}

当有两条或更多改动在等待时（比如升级之后，多个去处同时提出请求），同一张表有表头复选框，一开始什么都不会被选中。勾选你要答复的改动：操作栏显示“已选 2/3”，并提供 **拒绝 2** 和 **批准 2…**；什么都没勾选时，按钮是 **全部拒绝** 和 **全部批准 3…**。按下 **批准…** 会直接发起一次 Touch ID 或登录密码验证，系统提示会写出前几项并说明还有多少项；没有第二个确认步骤，因为这张表已经列出了这次确认涵盖的每一项改动。随后各行会显示每一项的结果：**已批准**或**已跳过**。在你打开清单之后目标发生变化的改动会被跳过并继续等待，已不在等待的也会被跳过；你看过的清单之外的任何东西都不会被批准。关闭保护从不属于批量操作，需要单独批准。**拒绝** 不需要在场验证。

拒绝对该目标一直有效：密钥继续被扣着，遇到它的服务器或命令会被告知“已被拒绝”（`SECRET_BINDING_REJECTED`），而不是“有东西在等”；使用这个密钥的页面会显示它已被拒绝。拒绝会弹出一条提示，审批对话框不再列出被拒绝的改动。要让问题重新摆到你面前，在显示拒绝的地方点**重新申请**（自定义工具分组的横幅；`coffer run` 则是 **允许 coffer run…**），或运行 `coffer approval ask-again <id>`，或者更改目的地。重新申请不需要在场验证，因为它不授予任何东西；在桌面应用里，这个按钮会直接弹出 Touch ID 并批准。一条审批最终的状态是 `approved`、`rejected` 或 `superseded`——后者表示它针对的资源被删除了，或已经换了目标，而新目标会另外发起一条新的审批。

### 在命令行上 {#on-the-command-line}

让某个密钥进入等待的命令，比如注册第二个引用了已发往别处的密钥的服务器，会保存改动，在标准错误上打印审批 id 和批准它们的命令，并以 `9` 退出：

```text
waiting for approval: <id>
next: coffer approval approve <id>
```

加上 `--json` 时，同样的内容打印为 `{"status": "pending_approval", "approval_ids": [...], "next": "coffer approval approve …"}`。`coffer secret set` 本身从不等待：它立即存入值并以 `0` 退出。

`coffer approval` 系列命令做的就是审批对话框做的事：

| 命令 | 作用 |
| --- | --- |
| `coffer approval list` | 待处理的审批，最新的在前。`--status approved`、`rejected`、`superseded` 或 `all` 显示其他状态；`--destination <uid>` 只看一个资源的。 |
| `coffer approval show <id>` | 这条审批发送什么、发往哪个去处和目标，以及它的状态。 |
| `coffer approval approve <id>…` | 把恰好这些审批交给桌面应用，由应用自己发起 Touch ID 或登录密码验证。 |
| `coffer approval reject <id>…` | 拒绝它们。和 **拒绝** 一样，不需要在场验证。 |
| `coffer approval ask-again <id>` | 把一条被拒绝的请求重新摆到你面前，作为同一目标的一条新的待批准审批。不需要在场验证。 |

`coffer approval approve` 自己什么都不批准。它在守护进程那里留下一个请求并等待；桌面应用取走请求，从守护进程读取每条审批，弹出系统提示，写明每项改动、它的密钥、发往哪里（包括自定义工具的环境）和目标，只有你确认后才应用这些审批。这次授权只能用于一个请求，并且绑定在询问你时每条审批所指的目标上：如果在你回答之前目标变了，什么都不会被应用（`APPROVAL_TARGET_CHANGED`），这条审批会重新询问。随后命令从守护进程读回每条审批的状态并退出：

- 全部批准时为 `0`；
- 你取消了、验证失败，或在 `--timeout`（默认 120 秒）内无人应答时为 `11`；每条审批都继续等待；
- 桌面应用没在运行且无法启动时为 `12`（`CLI_APP_UNAVAILABLE`）。最近没有应用向守护进程报到时，命令会启动它（`--no-launch` 可以阻止），最多等 30 秒；在没有应用或不是 Mac 的机器上，什么都不会被批准。

只有每个 id 都被点名且仍在等待时，多个 id 才共用一次提示；点名一条已不在等待的审批，命令会在任何提示之前被拒绝。关闭保护总是单独提示。没有任何参数（`--yes`、`--force` 或别的）能跳过验证，也没有任何东西去点击或脚本操控应用窗口。

智能体遇到退出码 `9` 时，应该告诉你它改了什么、哪些审批在等待，可以运行 `coffer approval approve <id>` 让提示出现在你的屏幕上，但不应重试这次改动。

### 关闭保护 {#switching-the-protection-off}

`secrets.require_approval` 默认**开启**。打开它立即生效。关闭它则要在桌面应用里等一条审批；关闭期间，每个新去处都会不经询问直接批准，唯独 `coffer run` 的允许不会这样批准。除此之外——没有任何环境变量、文件或参数——能把它关掉。开关在**设置 › 安全**的**审批**一节；浏览器里它显示为**在 Coffer 桌面应用中关闭**。

## 列出你的密钥 {#list-your-secrets}

```sh
coffer secret list
```

[密钥页面](#the-secrets-page)显示同一份列表。表格有一个 **Name** 列，显示每个密钥的名称，`--json` 则为每个密钥附带 `ref`、`uri`、`label`、`description`、`created_for`（为之生成它的资源的 uid，若有）、`locked`（已存储，但这台 Mac 的主密钥打不开它）、`created_at` 和 `last_used_at`，以及 `cited_by`——每个引用方连同它的类型、名称和引用该密钥所用的**槽位**。列表包含存储中保存的每个 ref 和每个资源引用的每个 ref，以及各自的使用方——资源、文件中引用了 `coffer://secret/<id>` 的技能、等待审批的去处——没有任何东西在用的密钥标为 `(unreferenced)`。每个托管智能体的模型代理令牌（`proxy-token/<智能体名>`）不在列表里：它由 Coffer 生成、由智能体自己取用，没有需要你填写、替换或引用的东西。**Readable by local processes** 为 `yes` 表示：以你身份运行的其他程序，能在 Coffer 放置该值的地方读到它——你已允许 `coffer run` 使用的独立密钥（它会进入子进程的环境），以及 stdio MCP 服务器环境中的每个密钥。各列的含义见[密钥存储 → 列出与查看](/zh/guides/secret-store#list-and-inspect)。

只要还有资源引用某个密钥，或还有技能文件引用它的 URI，删除就会被拒绝；报错会列出它们。

Coffer 每次为了使用而解密一个密钥——服务器启动、消息渠道连接、取用提供商的 Key、同步推送、`coffer run`——都会在[活动](/zh/guides/activity)里记录 `secret_resolved`，写明谁用了它以及用的槽位，从不记录值。同一个密钥和去处每分钟最多记录一次。可以在活动里查看，或用 `coffer log audit --event-type secret_resolved`。

## 主密钥及其备份 {#the-master-key-and-its-backup}

每个密钥都用同一把主密钥加密，它放在一个只有 Coffer 签名二进制能读的钥匙串条目里。其他程序既拿不到访问权限，也不会弹出可点击的对话框。守护进程读取时不询问，所以在崩溃后或登录时能无人值守地启动。

在场验证守护的是“让明文出去”的操作，而不是主密钥本身：这就是守护进程从不等你的原因。

**在桌面应用中备份主密钥**（设置 › 安全）：选一个口令，用 Touch ID 或登录密码确认，选一个文件夹，应用就会把受口令保护的 `coffer-master-key.cfk` 以权限 `0600` 写进去，并以 `master_key_exported` 记入审计。`coffer secret backup-key` 会在应用里打开同样的备份流程，口令在那里输入、文件夹在那里选择，然后等待：文件写出后它打印写到了哪里（退出 0），如果你关闭对话框，它以 `11` 退出，什么都没写。没有任何命令或浏览器页面自己写出备份。在另一台机器上用**设置 › 安全**里的**导入主密钥**（或用 `coffer secret import-key` 在应用里打开它；在应用里同样要 Touch ID）安装备份——见[密钥存储 → 把主密钥带到另一台机器](/zh/guides/secret-store#carry-the-key-to-another-machine)。钥匙串是唯一的副本，所以一定要做备份。
