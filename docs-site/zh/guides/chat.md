# 对话 {#conversations}

**对话**页面（以前叫 Chat）是你在 Coffer Web 界面里和受管智能体（Claude Code 或 Codex）交流的地方。本指南讲如何发起对话、选择模型和推理强度、一个轮次在流式输出时是什么样子、如何停止和排队，以及这个页面和智能体自己的会话、和你的[消息渠道](/zh/guides/channels)是什么关系。

## 对话页面用来做什么 {#what-conversations-is-for}

这个页面通过智能体自己的运行时驱动你本来就在用的智能体：Claude Code 走 Claude Agent SDK，Codex 走 `codex app-server`。Coffer 不在中间插入自己的模型。除非你为轮次选了模型，否则它用的是智能体自己的登录和内置模型。

这个页面是看一个对话的一扇窗，IM 消息渠道是另一扇。你在手机上通过 Telegram 或 SeaTalk 发起的对话会出现在对话页面上，你可以在这里看它的轮次流式输出、停止它们、继续打字。智能体分辨不出一个轮次来自哪扇窗。

::: info 没有 CLI
没有 `coffer chat` 命令组。对话可以从对话页面、从消息渠道，以及通过 `/api/v1/chat` 下的 REST API 访问。
:::

## 前提条件 {#prerequisites}

- 守护进程正在运行。用 `coffer open` 或[桌面应用](/zh/guides/desktop-app)打开界面。
- 在**智能体**页面至少登记了一个受管智能体，并且它的 CLI 已装在这台机器上。见[智能体](/zh/guides/agents)。
- 智能体已按你在终端里使用它的方式登录。Claude Code 需要先运行一次 `claude` 并完成 `/login`。

你**不需要**[模型提供商](/zh/guides/providers)。提供商只是可选的覆盖；没有它，智能体就用自己的登录运行。

如果没有可用的受管智能体，页面显示**没有可用的受管智能体**而不是输入框。这台机器上还没装任何受支持的智能体时，它提供**复制提示词**：这是守护进程写的一段提示词，能让任何助手去安装 Claude Code 或 Codex（只能复制，因为 Coffer 此时还没有智能体可交付）。装好但还没添加时，它会链接到**智能体**页面，你在那里添加。

## 发起对话 {#start-a-conversation}

1. 在侧边栏打开**对话**（在**运行**下）。页面打开时是对话列表，没有欢迎页或建议页。
2. 点页面标题旁的**新建对话**。对话框会问两件事：
   - **智能体**：只提供已安装、且已在「智能体」页面添加（并启用）的智能体。没安装、或装了但没添加的不会出现；一个都没有时，草稿会链接到**智能体**页面。
   - **工作目录**：智能体工作的文件夹（见[工作目录](#working-directory)）。
3. 点**开始**。草稿在 `/conversations/new` 打开，页头显示智能体、它的模型和推理强度，以及文件夹。
4. 输入消息，按 **Enter**。**Shift+Enter** 换行。

对话也可以从应用里其他地方的**交给智能体**发起，比如[命令行工具](/zh/guides/clis)页面报告某个命令缺失时。会打开同一个对话框，草稿的消息框里已经放好了 Coffer 为这件事写的提示词。读一遍，想改就改，然后按 **Enter**；在你按之前不会发送任何东西。

第一次发送才会创建对话。打开草稿再离开，什么都不会创建。对话以你写的第一句话命名；你随时可以重命名，Coffer 不会覆盖你起的名字。

打开的对话是 URL 的一部分：`/conversations/<id>`，所以刷新、书签或第二个标签页都会重新打开同一个对话。指向已删除对话的链接会显示**未找到该对话**，并带一个**新建对话**按钮。

### 工作目录 {#working-directory}

对话的工作目录在**新建对话**对话框里选：用**浏览…**选一个文件夹，或者输入、粘贴它的绝对路径。对话框默认打开你上次用的文件夹。留空的话，轮次在 Coffer 管理的工作目录 `~/.coffer/content/workspace` 里运行，首次使用时创建。草稿的页头会显示对话将使用的文件夹。

对话的智能体和工作目录在创建时就固定了，因为智能体的会话属于那一个目录。要换个地方工作，就新建一个对话。

::: tip
智能体以完全权限运行，所以它也能读写工作目录之外的东西；工作目录只是它开始的地方，也是它会话所在的地方。
:::

## 选择模型和推理强度 {#choose-the-model-and-reasoning-effort}

页头里智能体旁边有两个控件，草稿和已打开的对话里都有。新建对话框不问这两项：新对话从智能体自己的设置（它的**模型**标签页）开始，你在这里切换。

| 控件 | 标签 | 提供什么 |
| --- | --- | --- |
| 模型 | **智能体模型** | 先是**默认**，然后是平台为这个智能体提供的模型，最后是对话当前的值（如果不在列表里）。 |
| 推理强度 | **推理强度** | **智能体默认**，然后是所选模型报告的档位。模型不报告任何档位时，这个控件隐藏。 |

模型列表是智能体自己的目录，从已安装的 CLI 读取。如果这个智能体运行在某个[模型提供商](/zh/guides/providers)上，列表就换成该提供商精选的文本模型。选择器是固定的下拉框，不接受自由输入。

- **默认**会清除模型，智能体按它自己的配置运行。
- 改动从下一个轮次生效。模型和推理强度每个轮次都会重新读取；智能体和工作目录不会。
- 每个轮次都带一段简短说明，告诉智能体 Coffer 让它用的是哪个模型，所以问智能体「你是哪个模型？」会得到正确答案。

对话创建后，它的智能体以图标和名称显示，不能更改。要和另一个智能体交流，就新建一个对话。

## 观看一个轮次 {#watch-a-turn}

回复会在智能体写的同时流进对话，显示在智能体的图标、名称和时间下面。流式输出时：

- 助手的文字按 GitHub 风格的 Markdown 渲染。单个换行保留为换行，表格渲染成表格，每个代码块都有自己的**复制**按钮。
- 每次工具调用是一张卡片，按智能体调用的顺序夹在前后文字之间。卡片写明工具名和调用对象（文件、模式、命令），在结果返回前显示**运行中**，之后显示**完成**或**出错**。展开可以看**输入**和**结果**。
- 回复完成后，**改动的文件**会列出它的工具调用写过的每个文件，以及各自增删的行数。
- 完成的助手消息会显示 token 用量（比如 `18.2k in · 1.4k out`），并记录生成它的模型。
- 如果你往上滚了，**跳到最新**会带你回到实时的末尾。

轮次在守护进程里作为独立任务运行。关掉标签页、断了 Wi-Fi 或刷新都不会让它停下：回复会跑完并保存，你回来时页面会重新订阅，并从头重放正在进行的轮次。如果实时流在轮次中途断开，页面会自己重连；五次失败后，它会显示**与守护进程的实时连接已断开**和**重新加载对话**，点后者会显示这个轮次到目前为止写的全部内容。

## 轮次进行中继续发送 {#send-while-a-turn-runs}

输入框从不锁定。回复流式输出时，它的占位文字是**回复——会排队到这一轮结束**。

1. 再发一条消息。它会进入对话的待处理队列，作为单独一行显示在**队列中：**下面。
2. 当前轮次结束后，每条排队的消息按顺序各自作为一个轮次运行。消息从不合并。
3. 要修改排队的消息，选**编辑排队消息**。它会离开队列回到输入框；再次发送会把它放到队列**末尾**。
4. 要删掉一条，选**从队列移除**。

队列在所有入口之间共享。手机在轮次中途发来的消息会出现在同样的排队行里，消息渠道的 `/status` 也会把你在浏览器里排队的消息算进去。

::: warning
待处理队列存在守护进程的内存里。重启守护进程会丢掉还没开始的消息。
:::

## 停止轮次 {#stop-a-turn}

轮次运行时，**发送**会变成**停止**。停止会：

- 结束这个轮次，保留它已经产生的文字，存成一条完整的消息；
- **暂停**待处理队列，这样下一条排队的消息不会立刻冲进你刚停掉的轮次。

你发送的下一条消息（无论来自页面还是消息渠道）会恢复暂停的队列。**停止**对对话里的任何轮次都有效，包括从手机发起的轮次。它和消息渠道里的 `/stop` 是同一个操作。

## 轮次失败时 {#when-a-turn-fails}

失败的轮次会把进行中的气泡替换成输入框上方的一条错误横幅，带**重试**（重新发送失败的那条消息及其附件）和**关闭**。智能体在失败前写的内容会留在对话里，标记为**该回复未完成。**

守护进程在运行前就拒绝的消息（比如某个附件已经不可用）不算失败的轮次：横幅会说明原因，但不带**重试**，消息连同文字和文件留在输入框里，你修好后可以再发。新对话的第一条消息也是这样。

除了智能体自己报告的错误，Coffer 还会报告三种自己的失败：

| 错误 | 含义 |
| --- | --- |
| `stream_ended` | 智能体的事件流在没有完成事件的情况下结束了：它的进程在轮次中途退出或断了连接。 |
| `turn_timeout` | 智能体在空闲窗口内没有产生任何事件：`COFFER_TURN_IDLE_TIMEOUT_SECONDS`，默认 300。设为 `0` 可关闭这个看门狗。 |
| `daemon_stopped` | 轮次运行时守护进程关闭了。 |

轮次从不悄无声息地结束。如果守护进程被直接杀掉，到那时为止流出的文字最多每秒保存一次，下次守护进程启动时会把未完成的回复标为失败，而不是显示成仍在输出。

如果 Claude Code 没有登录，横幅会说明，并提示你运行 `claude` 完成 `/login`。

## 回复消息渠道里的对话 {#replying-to-a-channel-s-conversation}

[消息渠道](/zh/guides/channels)打开的对话就是一个对话，不管你在哪个屏幕上打字。你在对话页面上回复它时，回复也会发回它来的那个聊天，这样手机上显示的是完整的来回，而不只是它自己那一半。

- 发送前，回复框上方有一行说明回复还会发到哪里，比如**同时发送到 SeaTalk · 🧵#1 deploy check**，或者**回复只留在 Coffer**，旁边的 **?** 会说明原因。
- 回复会以 `(from Coffer) …` 的形式发到那个聊天或线程里，智能体的回答也跟在那里，和你在手机上打字得到的回答完全一样。
- 回复只会发到对话所属的那个聊天和线程，绝不会发到别处。

位于**群组主聊天**里的对话永远不会被镜像：输入框会说明回复只留在 Coffer。主聊天是整个群都在看的地方，你在工位上打的一句回复，加上群里没人问过的回答，不该丢到所有人面前。私聊、它的并行线程和群组线程是你自己可以继续的，所以会镜像。

如果消息渠道暂时发不出去（它没在这台机器上运行，或者平台拒绝了），回复不会丢。它会被标为**尚未送达*平台***（比如**尚未送达 SeaTalk**），智能体仍在页面上回答，等消息渠道再次运行时，回复和回答会按顺序发到聊天里。送达后标记消失。

只有发送会镜像。轮次失败后的**重试**会在页面上重新运行，但不会把消息再发到聊天里一次。

## 附件 {#attachments}

一条消息最多容纳 32,768 个字符的文字和 10 个附件。在输入框里有三种添加附件的方式：

- 点消息框旁边的回形针，选一个或多个文件；
- 把文件拖到输入框上：拖动时只有输入框会变化，边框变成强调色，并显示**松开以添加附件**；
- 把图片（比如截图）粘贴进消息框。

每个文件一添加就开始上传，显示为一个带文件名和大小的标签。超过大小上限的文件，或者第十个之后的文件，根本不会被添加：回复框下方会有一行说明是哪个文件、为什么。有文件在上传时，或者还挂着一个被守护进程拒绝的文件时，**发送**保持禁用：那个文件的标签会说明失败原因，用 **×** 移除它之后就能发送其余的。一条消息可以只有文件没有文字；它会存成一行列出文件名的简短文字。

| 上限 | 值 |
| --- | --- |
| 单个文件大小 | 20 MB |
| 每条消息的文件数 | 10 |
| 接受的类型 | 图片、音频、文档（PDF、Word、PowerPoint、Excel、RTF、EPUB、CSV），以及任何 UTF-8 文本文件，比如源码、Markdown、JSON 或日志 |

视频、压缩包和其他二进制文件会被拒绝，因为两个智能体都无法在轮次里使用它们。

图片的类型是从它的字节里读出来的，而不是看文件名或浏览器报告的类型：存成 `photo.png` 的 JPEG 会以 `image/jpeg` 保存和显示。声称是图片但不是 PNG、JPEG、GIF 或 WEBP 的文件（比如 HEIC 照片或 SVG）会作为普通文件保存（`application/octet-stream`）。

附件也可以通过[消息渠道](/zh/guides/channels)进入对话：你发给机器人的照片、文件或语音消息。两种来源在对话里都显示为写明文件名和类型的标签，重新加载后也一样。

智能体如何收到附件取决于附件类型，不管它是怎么来的：

- **图片**：PNG、JPEG、GIF 或 WEBP 图片，如果编码发送后不超过 5 MB（磁盘上约 3.75 MB），Claude Code 会内联收到，作为它能看到的图片。更大的图片或其他格式的图片会以文件路径的形式交给 Claude Code，这样轮次仍能运行。Codex 总是收到文件路径。
- **文档**（PDF、Office 格式、epub、rtf）：提取成文字放进提示词，所以每个智能体都能读到内容。如果无法提取或提取失败，智能体收到文件路径。
- **音频**：在**设置 › 通用 → Coffer 自用模型**下打开了**语音转文字**时，会转写成文字。关闭转写时，什么都不会离开你的机器，智能体收到的是音频文件。

文件字节留在磁盘上；对话只存一个引用，之后的轮次从那里读回文件。在对话页面添加的文件存在 `~/.coffer/content/chat-media`，消息渠道收到的文件存在 `~/.coffer/content/channel-media`；两者都在最后修改 30 天后清理。之后对话里仍显示标签，但智能体再也打不开这个文件。

重试失败的轮次会连同附件重新发送消息。如果其中某个文件已被清理，重试会被拒绝并报错说明，不发送任何东西：重新添加文件，发一条新消息。

## 管理对话 {#manage-conversations}

`/conversations` 列出所有对话，不管是谁打开的，按最近活动从新到旧排列，分在**今天**、**昨天**和更早的日期下。对话在轮次开始时就会移到顶部，不只是在轮次结束时。每一行显示：

- 标题，轮次进行中时带**运行中**，下面是最新消息的第一行；
- **来源**：在本页面发起的对话显示 **Coffer**；[消息渠道](/zh/guides/channels)打开的对话显示平台和它在聊天里的位置：`SeaTalk · DM`，并行线程是 `SeaTalk · DM · 🧵#2`，还有 `SeaTalk · Group › thread`、`Telegram · Group › topic`。鼠标悬停在标记上可以看到消息渠道的名称；
- **智能体**和**最近活动**。

列表上方的筛选条件是 URL 的一部分，所以筛选后的列表就是一个链接：

- **全部来源 / Coffer / SeaTalk / Telegram**：`?source=seatalk`。
- **全部智能体**或某个智能体：`?agent=codex`。
- 某个消息渠道：`?channel=<uid>`。消息渠道页面上某个渠道的**来自*名称*的对话**链接会打开它；列表保留来源切换，并在智能体筛选旁显示一个**消息渠道：*名称***标签，点它的 **×** 清除。没有对话符合筛选条件时，**清除筛选**会重置它们。
- **已归档**：显示已归档的对话，而不是活跃的对话。

打开一个对话时，列表会放在它旁边，筛选条件相同，还有一个**搜索对话**框，按标题筛选已加载的列表。两者之间的分隔线可以拖动。对话的页头有一个 **⋯** 菜单：

| 操作 | 效果 |
| --- | --- |
| **重命名** | 设置一个 Coffer 不会覆盖的标题。 |
| **归档** | 立即移到**已归档**，不删除任何东西。 |
| **恢复** | 把已归档的对话放回活跃列表。 |
| **删除…** | 先确认，然后删除 Coffer 保存的对话及其消息，并取消其中正在运行的轮次。智能体自己的会话文件不受影响；想保留一个对话就归档它。 |

已归档的对话以只读方式打开：历史正常显示，输入框以及模型和推理强度控件被禁用，取而代之的是**恢复以继续对话**。

### 保留期限 {#retention}

Coffer 会把 7 天没有新消息的对话归档，并在归档 30 天后删除它们。删除窗口可以在**设置 → 数据 → 历史记录 → 对话**下修改，或设为**永久保留**；归档窗口用 `coffer config set retention.conversations_archive <days>` 设置。归档可以撤回，删除不能。

## 对话和智能体自己的会话 {#chat-and-the-agent-s-own-sessions}

每个 Coffer 对话背后是智能体的一个真实会话。Coffer 把智能体的会话 id 存在对话上，每个轮次都恢复这个会话，所以智能体在轮次之间保留自己的上下文，和在终端里完全一样。如果智能体不再认识存下的会话 id，Coffer 会把这个轮次作为全新会话重试一次，而不是直接失败。

这个对话有两份记录：

- **Coffer 的对话**：消息、工具调用、结果、模型和 token 用量，存在 Coffer 的历史数据库 `runs.db` 里。对话页面显示的就是它，它是智能体做了什么的记录。轮次不会写进审计日志。
- **智能体自己的会话文件**：由智能体自己保存，和任何会话一样。智能体的详情页在**智能体 → *智能体* → 对话**（**Transcript sessions**）下列出这些文件，连同你直接在终端里跑的会话。

每个对话只有一个所有者：你，不管你在哪个屏幕上。对话不支持多人共享一个对话；让手机能驱动对话的消息渠道配对，和你的浏览器会话是同一个信任决定。

## 智能体从保险库拿到什么 {#what-the-agent-gets-from-the-vault}

对话轮次运行在同类型已登记智能体的配置目录上（每种类型一个）。Coffer 把[技能](/zh/guides/skills)投递到这个目录，并在这里装它的 MCP 条目，所以对话里的智能体拥有和你终端里一样的 Coffer 技能和 [MCP 服务器](/zh/guides/mcp-servers)。这个智能体的配置目录不在标准位置时，Coffer 会为轮次设置 `CLAUDE_CONFIG_DIR` 或 `CODEX_HOME`。

在智能体自己的系统提示词之后，Coffer 按以下顺序追加：

1. 来自消息渠道的轮次：一段说明，告诉智能体它在聊天渠道上，回复要简短，而且它不能点你电脑上的对话框。
2. 来自消息渠道的轮次：对话工作目录和 `global` 的[记忆](/zh/guides/memory#in-channel-turns)索引，以及笔记所在的位置。
3. 每个轮次：说明 Coffer 让智能体用的是哪个模型。

从对话页面发出的轮次不追加记忆；智能体连接到 Coffer 后，会通过它自己设置里 Coffer 的记忆 Hook 收到记忆。

::: danger 完全权限
对话以 `bypassPermissions` 运行 Claude Code，以 `approvalPolicy: never` 和 `sandbox: danger-full-access` 运行 Codex。Coffer 不会让你逐个批准工具调用。把消息渠道配对到你自己的账号，就是来自 IM 的轮次的关卡；见[消息渠道](/zh/guides/channels#security)。
:::

## 工作原理 {#how-it-works}

发送是「发出即返回」：`POST /api/v1/chat/conversations/{id}/messages` 启动轮次或把它排队，立即返回 `202`。页面从一个 server-sent-event 订阅 `GET .../events` 读取每个轮次的输出，它会给晚到的订阅者重放正在进行的轮次，然后实时跟随。你发起的轮次和手机发起的轮次走同一条路径。断开的订阅会退避重连，尝试次数有上限，超过就放弃。

事件名是 `turn_start`、`text_delta`、`tool_call`、`tool_result`、`turn_done`、`turn_error` 和 `queue_changed`。设计见[对话与轮次](/zh/architecture/chat)。

## 故障排查 {#troubleshooting}

**智能体显示为不可用。** 要么它的 CLI 不在你的 `PATH`（登录 shell 的 `PATH` 与守护进程自己的合并）上，要么「智能体」页面里没有添加该类型的已启用智能体。安装 CLI，或添加、启用该智能体。「对话」只运行 Coffer 管理的智能体。

**每个轮次都以 `stream_ended` 失败。** 智能体进程在轮次中途退出了。先确认智能体在终端里能正常工作，再到**活动 → 守护进程**查看底层错误。

**没有流式输出，回复一下子全部出现。** Claude Code 轮次需要支持部分消息的 CLI。SDK 使用自己内置的 CLI；如果它缺失、而 `PATH` 上的 `claude` 又太旧，轮次会在连接时失败。请更新 Claude Code。

**页面显示一条横幅而不是对话。** 守护进程无法访问。见 [Web 界面](/zh/guides/web-ui#when-the-daemon-is-not-reachable)。
