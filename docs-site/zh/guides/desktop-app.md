# 桌面应用 {#desktop-app}

Coffer 桌面应用是一个 macOS 应用，它在原生窗口里承载 Coffer 的 Web 界面，带 Dock 图标和菜单栏图标，会替你找到或启动守护进程，并保持自身更新。它也是唯一能让你看到密钥值、备份主密钥，或批准把密钥发往新去处的地方。本页讲如何安装和更新它、它比浏览器标签页多了什么、菜单栏、在场校验和批准、它如何连接守护进程，以及退出应用和守护进程的生命周期是什么关系。

## 它多了什么 {#what-it-adds}

应用显示的界面和浏览器标签页里守护进程地址上的一样（由同一份 `frontend/dist` 构建），所以每个页面的表现都完全相同。它多出来的，是浏览器标签页自己做不到的事：

- **一个真正的应用。** 有 Dock 图标、能 Cmd-Tab 切换的窗口，还有一个菜单栏图标，窗口关闭后仍常驻，告诉你守护进程是否在运行、有几件事需要你处理。窗口有自己的标题栏，带侧边栏开关和前进/后退箭头（见 [Web 界面](/zh/guides/web-ui#the-sidebar)）。
- **检测或启动。** 启动时它会连接正在运行的守护进程，或者启动一个。你永远不需要知道端口。
- **不用终端也能恢复。** 菜单栏和离线横幅上都有**重启守护进程**。浏览器页面做不到这一点：已经挂掉的守护进程没法提供放这个按钮的页面。
- **版本检查。** 如果它连上的是旧版本留下还在运行的守护进程，会发出警告。
- **同步提醒出现在你看得到的地方。** [保险库同步](/zh/guides/vault-sync)需要你时，菜单栏的计数、Dock 角标和一条通知都会告诉你。
- **更新。** 它在启动时以及每六小时检查一次是否有更新的签名版本，你在**设置 › 关于**里选**下载并重启**时安装。见[更新](#update)。
- **在场校验。** 显示或复制密钥、备份主密钥、导入主密钥、批准一项批准请求，都会先要求 Touch ID 或你的登录密码。浏览器无法做这种校验，所以浏览器标签页在这些地方显示 **Open in Coffer app**。见[在场校验和批准](#presence-checks-and-approvals)。
- **批准提醒。** 有密钥等着被发往新去处时，应用会发一条通知，并打开一个面板让你处理。
- **命令行请求的在场校验。** `coffer approval approve`、`coffer secret reveal`、`coffer secret backup-key` 和 `coffer app update …` 会在守护进程那里留下一个请求；应用大约一秒内取走它，运行和自己按钮一样的流程，所以 Touch ID 提示、显示的值和备份口令都留在应用里。命令发现应用没开时会启动它。见[密钥 → 在命令行上](/zh/guides/secrets#on-the-command-line)。

其他一切（在编辑器里打开文件、选择文件夹）都和在浏览器里一样，走守护进程的 HTTP 路由。

::: info 平台
桌面应用只为 Apple silicon 上的 macOS 构建。其他平台请用 CLI 安装，并在浏览器里打开守护进程的地址（`http://127.0.0.1:<port>`）。
:::

## 安装 {#install}

::: warning 还没有带标签的正式版本
`.dmg` 随带标签的 GitHub release 发布，而目前还一个都没有。在此之前，请自己构建应用（见[从源码构建](#build-from-source)）。
:::

1. 从项目的 [Releases](https://github.com/wyx-sg/Coffer/releases/latest) 页面下载 `.dmg`。
2. 打开 `.dmg`，把 **Coffer** 拖进**应用程序**。
3. 用项目的 Developer ID 签名的版本（`Coffer-aarch64-apple-darwin.dmg`）经过公证，能正常打开。没有签名构建的版本名为 `Coffer-unsigned-aarch64-apple-darwin.dmg`，对于从浏览器下载的这种副本，macOS 会以 *"Coffer is damaged and can't be opened"* 拒绝打开。它并没有损坏。清除隔离标记即可：

   ```sh
   xattr -dr com.apple.quarantine /Applications/Coffer.app
   ```

4. 从应用程序里打开 Coffer。

应用是自包含的：它的包里带着四个 frozen 二进制文件 `coffer`、`coffer-daemon`、`coffer-mcp-shim` 和 `coffer-seatalk-bridge`，不需要事先安装任何东西。

### 应用也会安装 CLI {#the-app-installs-the-cli-too}

首次启动时，守护进程会把这四个二进制文件复制到 `~/.coffer/bin`。把这个目录加进你的 `PATH`，就能在终端里用 `coffer`，MCP 客户端也能解析到 `coffer-mcp-shim`：

```sh
export PATH="$HOME/.coffer/bin:$PATH"   # add this to your shell profile
```

应用本身从不写 `~/.coffer/bin`；这件事由守护进程做，所以两者永远不会争抢这个目录。

### 更新 {#update}

应用会自我更新。它在启动 30 秒后检查最新 GitHub release 的更新清单，运行期间每六小时再检查一次，不会打扰你：**设置 › 关于**会显示上次检查的时间、有没有新版本以及它的发布说明，侧边栏底部上方的卡片会带版本号提供**重启**。在你在关于页选择**下载并重启**或在卡片上选择**重启**之前，什么都不会下载。之后应用会下载更新，用内置在应用里的密钥校验签名（签名校验不过的更新会被拒绝），替换自身，重新启动，并重启上一个版本的守护进程，让新的守护进程接手。智能体会自己重新连接。

- 关于页上的**检查更新**会立即检查。
- 关于页上的**自动检查**可以关掉启动时和每六小时的检查；手动检查仍然可用。
- 检查失败时（没网、清单无法访问），关于页会说明原因，保留上次成功检查的时间，不改变任何东西。失败也会写进 `~/.coffer/logs/daemon.log`。
- 没有更新密钥的构建（所有从源码构建的版本，以及项目有更新密钥之前发布的版本）会说明它不检查更新。更新方式是把新的 `.dmg` 装在它上面，再选**重启守护进程**。
- 在浏览器里，关于页只会说明更新由桌面应用安装。

## 在场校验和批准 {#presence-checks-and-approvals}

Coffer 的[密钥边界](/zh/guides/secrets)把密钥的值、以及把它发往新去处的决定，都留给坐在这台 Mac 前的人。应用就是这个人操作的地方：

| 操作 | 在哪里 | 做什么 |
| --- | --- | --- |
| **显示**或**复制**密钥 | 应用里的该密钥 | 显示或复制这一个值。审计记录为 `secret_revealed`。 |
| **备份主密钥** | 应用 | 先让你输入一个口令，然后把 `coffer-master-key.cfk`（用该口令加密的主密钥）以 `0600` 权限写进你选的文件夹。审计记录为 `master_key_exported`。见[密钥存储 → 备份主密钥](/zh/guides/secret-store#back-up-the-key)。 |
| **批准** | 批准面板 | 允许密钥发往新的去处或目标，应用一个替换后的值，或者关闭保护。 |

每个操作都单独校验一次，中间不记住任何东西：

1. macOS 要求 **Touch ID 或你的登录密码**。提示里会写明你在批准什么（"reveal the secret github/token"，或者批准请求自己的描述），所以按下之前先读一遍。
2. 之后应用才会向守护进程要一个针对该操作的一次性挑战，签名后发出请求。取消则什么都不发送。
3. 下一次显示或批准会再问一次。

**批准会主动找你。** 不管窗口是否打开，应用每 15 秒检查一次守护进程。每出现一个新的待批准请求，它就发一条通知 **Coffer 需要你批准**，正文写明是什么改动，窗口会打开批准面板。在那里你可以批准（需要上面的校验）或拒绝（不需要校验）。等待批准的命令会打印 `waiting for approval in the Coffer app`；什么会触发批准，见[密钥 → 批准](/zh/guides/secrets#approvals)。

::: warning 开发版构建
没有用 Coffer 的 Developer ID 签名的构建（所有从源码构建的版本，以及项目有 Developer ID 之前发布的所有版本）都是开发版：主密钥是一个你名下任何程序都能读取的文件，同一用户下的程序可以伪造应用的签名。应用在每个提示上都会标明 **Development build**。在没有 Touch ID 或 LocalAuthentication 的 Mac 上，开发版会改为在自己的窗口里弹一个对话框让你确认。见[安全模型 → 开发版构建](/zh/architecture/security#development-builds)。
:::

## 启动 {#launch}

打开应用时：

1. 它会寻找守护进程（见[它如何找到守护进程](#how-it-finds-a-daemon)），连接正在运行的，或者启动一个。
2. 在守护进程应答之前窗口保持隐藏，所以你永远不会看到一个什么都不能用的页面。如果守护进程已经在运行（比如作为[登录服务](#keep-the-daemon-running)），这一步是瞬间完成的。
3. 如果连不上任何守护进程，窗口仍会打开，并说明原因。

在真实保险库上，守护进程可能要花好几秒来解包、迁移并启动它的 MCP 服务器。应用给它启动的守护进程最多 90 秒来应答，之后继续按退避重试，所以启动慢会自行恢复，不用重启。

## 菜单栏 {#the-menu-bar}

Coffer 在菜单栏里的图标是 Coffer 标志，用菜单栏自己的颜色绘制，浅色和深色菜单栏都合适。总览里有事需要你时，图标旁会显示计数（超过九显示 **9+**），被你忽略的项不计入。计数随你的处理实时变化：窗口开着时，解决或忽略一项后几秒内就会减少（窗口关着时约 20 秒内），全部处理完后计数消失；没有守护进程运行时，它会**变暗并加删除线**。点击它打开菜单：

| 菜单项 | 做什么 |
| --- | --- |
| **守护进程运行中 · 端口 38470 · 1.0.0** | 只显示状态：守护进程的端口和版本，或者**守护进程离线**。 |
| **N 件事需要你处理** | 只在总览列出需要你处理的事时显示；打开总览。如果只有一个同步问题，会直接写出它，比如**同步需要处理 — 冲突**。 |
| **打开 Coffer** | 显示窗口并聚焦。 |
| **重启守护进程** | 停掉正在运行的守护进程，启动一个新的。没有守护进程运行时显示为**启动守护进程**。 |
| **退出 Coffer** ⌘Q | 退出应用。守护进程继续运行。 |

菜单刻意保持简短：对话、设置、**开机自启动**（在**设置 › 守护进程**里）和更新（侧边栏底部上方的卡片以及**设置 › 关于**）都从窗口里进入。菜单会自己跟随守护进程：每 10 秒读取一次守护进程状态，每分钟读取一次需要你处理的事项。

菜单、它的提示文字和同步通知使用你在**设置 › 通用**里选的界面语言（English 或中文）。切换语言会立刻更新菜单文字。窗口加载完成之前，它使用你的 macOS 语言。

关闭窗口会把应用收到菜单栏里，而不是退出。点击 Dock 里的 Coffer 会把窗口带回来。

当一轮同步需要人来处理时（等待确认、冲突、推送失败、运行失败，或者有机器还没加入），应用会在菜单栏图标旁显示计数，给 Dock 图标加角标，并发一条标题为 **Coffer 同步需要你处理**的 macOS 通知。

## 重启守护进程 {#restart-the-daemon}

使用菜单栏里的**重启守护进程**，或窗口离线横幅上的同名按钮。一次重启会：

1. 通过经过认证的关闭路由，让正在运行的守护进程关闭；
2. 等待端口释放；
3. 启动新的守护进程并等它应答。从横幅发起的重启会把新守护进程的连接直接交给窗口。

如果端口一直不释放，重启会报告这一点，而不是去启动一个绑定不了端口的守护进程。重启最多每 5 秒一次，从上一次**成功**的重启开始计算，所以失败的尝试可以立刻重试。

从菜单栏发起的重启没有地方显示消息；结果会写进 `~/.coffer/logs/daemon.log`。

## 它如何找到守护进程 {#how-it-finds-a-daemon}

应用按固定顺序解析守护进程，采用第一个适用的：

1. `~/.coffer/daemon.json` 指向的、能应答 HTTP 状态检查的运行中守护进程。应用连接它，不启动任何东西。
2. 应用包里的 `coffer-daemon`。
3. `~/.coffer/bin/coffer-daemon`。
4. 你 `PATH` 上的 `coffer-daemon`。
5. 否则，给出一条消息，列出它找过的位置以及如何安装 CLI。

运行中的守护进程排在最前，这样应用永远不会在你从终端启动的守护进程旁边再起第二个。用状态检查而不是只探测端口，可以避免把 38470 端口上无关的进程误认成 Coffer。

应用启动的守护进程：

- **比应用活得久。** 它与应用的进程分离，因为不管窗口开没开，智能体都在用它。
- **拿到你登录 shell 的 `PATH`。** 从 Finder 或 Dock 打开的应用只继承一个最小的 `PATH`；应用会在时限内向你的登录 shell 要真正的 `PATH`，这样基于 `npx` 和 `uvx` 的 MCP 服务器才能解析。

### 版本不一致 {#version-skew}

如果应用连上的守护进程版本和自己不同（通常是上一次安装留下还在运行的），它会继续和它一起工作，并在横幅上显示**守护进程版本过旧**。选**重启守护进程**，用应用包里的守护进程替换它。

## 它如何连接 {#how-it-connects}

窗口从应用包里加载界面，而不是从守护进程的地址加载。所以守护进程慢或不在时，你看到的是横幅而不是浏览器的连接错误，端口也从不出现在任何地方。

因为这个页面不是守护进程提供的，守护进程没法像对浏览器那样把令牌写进页面。于是应用从 `~/.coffer/daemon.json` 读取端口和令牌，通过进程内 IPC 调用交给页面，作为和浏览器页面收到的相同的两个值。页面先渲染，等值到了再应用。在交出令牌之前，以及每次需要在场校验的操作之前，应用还会确认它找到的守护进程确实是 Coffer 的：发一个随机 nonce，校验回答——只有持有主密钥的一方才算得出。校验失败，应用会停下并提示“This is not Coffer's daemon — nothing was sent”，不交出令牌、授权或任何值（见[安全模型](/zh/architecture/security#who-is-on-the-other-end)）。应用自己不存任何密钥：对于需要在场校验的操作，它在签名的那一刻读取主密钥，既不保留主密钥，也不保留任何由它派生的东西。

窗口的内容策略只允许向回环地址（任意端口）和应用自己的 IPC 通道发起网络请求；脚本和样式只来自应用包。

## 退出应用，保留守护进程 {#quit-the-app-keep-the-daemon}

用**退出 Coffer** 退出应用，只会关闭窗口和菜单栏图标。守护进程继续为你的智能体、消息渠道和同步服务。要停止守护进程本身，运行：

```sh
coffer daemon stop
```

### 让守护进程一直运行 {#keep-the-daemon-running}

打开**设置 → 守护进程 → 开机自启动**，守护进程会在你登录时启动，崩溃后自动重启，不管应用是否打开。打开后，应用启动时会连接已经在运行的守护进程，立刻打开。

## 日志 {#logs}

应用自己的记录（选了哪个守护进程二进制、握手是复用、启动还是失败、菜单栏发起的重启失败、更新检查或安装失败）以单行 JSON 写进 `~/.coffer/logs/daemon.log`，logger 名为 `coffer.desktop`，和守护进程自己的日志行放在一起。在**活动 → 守护进程**里查看，或者：

```sh
grep coffer.desktop ~/.coffer/logs/daemon.log | tail
```

## 故障排查 {#troubleshooting}

**"Coffer is damaged and can't be opened."** 清除隔离标记：`xattr -dr com.apple.quarantine /Applications/Coffer.app`。

**应用说找不到它的守护进程。** 应用包里的二进制文件缺失，没带它们构建的开发版会这样。安装 CLI，或者从正式版 `.dmg` 重新安装应用。

**横幅说守护进程没有运行，而且一直不消失。** 选**重启守护进程**。如果失败，到 `~/.coffer/logs/daemon.log` 里找 `coffer.desktop` 行。因为 38470 端口被占而拒绝启动的守护进程会写明占用它的进程；用 `coffer config set daemon.port <port>` 给 Coffer 换个端口。

**在终端里能用的 MCP 服务器，在应用启动守护进程后失败。** 登录 shell 的 `PATH` 探测超时或失败了，所以守护进程拿到的是 GUI 的最小 `PATH`。从终端启动守护进程（`coffer daemon start`），或打开**开机自启动**，然后重新打开应用；它会连接那个守护进程。

**界面看起来比守护进程旧。** 应用自带一份界面。安装版本匹配的 `.dmg`。

## 从源码构建 {#build-from-source}

`make desktop` 会构建 `Coffer.app` 和 `.dmg`。它需要 Rust 工具链，并先用 PyInstaller 构建四个二进制文件，所以大约要 50 分钟。产物没有签名。见[开发环境搭建](/zh/contributing/development)。
